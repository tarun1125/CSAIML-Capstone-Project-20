What this project is, in three sentences

A benchmark for turning a plain-English question into a MongoDB query. It compares three ways of adapting one small model (zero-shot, retrieval-augmented, and LoRA fine-tuned), then a larger hosted model, on 304 held-out questions across 23 databases. Every answer is graded by running the query against a live database and comparing the rows it returns, never by comparing text.

The one idea to carry into every interview

Grading by execution is what makes every number here trustworthy. A query can look completely different from the reference and still be right, or look almost identical and be wrong. String metrics can't tell those apart; running the query can. Finding a cheap, trustworthy oracle is most of the work in testing a system like this.

Fundamentals, from zero

Each idea below is used somewhere in this project. Read the ones you can't yet explain in two sentences.

1. The task: NL → query

The input is a question like "How many singers are there?" plus a database. The output is one line of Python that PyMongo can run, for example db.singer.count_documents({}). MongoDB stores documents (JSON-like records) in collections (like tables) inside databases. Two query styles appear:

  • find(filter, projection): select documents matching a filter and choose which fields come back.
  • aggregate([stage, stage, …]): a pipeline. Each stage transforms the stream: $match filters, $group groups and counts, $lookup joins another collection, $project reshapes, $sort, $limit.

The questions come from Spider, a public text-to-SQL benchmark. Its SQLite databases were converted into MongoDB collections, and the gold answers were hand-written as PyMongo queries.

2. Language models, tokens, decoding

A language model reads text as tokens (word pieces) and predicts the next token, one at a time. Decoding is how the next token is chosen:

  • Greedy (temperature 0): always take the most likely token. Deterministic on the same hardware and software. Used for every scored run here, so re-runs are comparable.
  • Sampling (temperature > 0): pick randomly in proportion to probability. Higher temperature means more random. Used only for self-consistency (below).

A model's log-probability for a token measures how confident it was. The mean log-probability over an answer's tokens is one confidence signal. Self-consistency is another: sample the answer k times and measure how often the samples agree.

3. Prompting: zero-shot, few-shot, schema

  • Zero-shot: instructions plus the question, no examples. Here the baseline also gets the schema of all 23 databases (so it has to find the right one itself).
  • Few-shot: include example question → query pairs in the prompt so the model copies the style.
  • Schema: the list of collections and fields (with types). Without it the model invents field names.

4. Embeddings and cosine similarity

An embedding model turns a sentence into a fixed-length list of numbers (a vector) so that sentences with similar meaning land close together. This project uses all-MiniLM-L6-v2, which gives 384 numbers per sentence.

Cosine similarity is the angle-based closeness of two vectors: 1 means same direction, 0 unrelated. If every vector is scaled to length 1 first (L2-normalised), cosine similarity equals the plain dot product, which is cheaper. That's why the index here is an "inner product" index over normalised vectors.

Mean pooling: MiniLM produces one vector per token; averaging them (ignoring padding) gives one vector for the sentence.

5. Vector search: FAISS, exact vs approximate

FAISS is a library for finding the nearest vectors fast. IndexFlatIP compares the query against every stored vector: exact, and plenty fast for 1,213 vectors. Approximate indexes (HNSW, IVF) skip most comparisons to handle millions of vectors, at the cost of sometimes missing the true nearest one. At this scale exact search costs nothing, so there's no reason to accept that error.

6. RAG: retrieval-augmented generation

Instead of hoping the model knows the answer, retrieve relevant material and put it in the prompt. Here the "material" is the 10 most similar past questions with their correct queries, plus the full schema of the database those examples point to. The model then writes a query in the same style.

7. Keyword search (BM25), hybrid search and RRF

BM25 scores documents by shared words, weighting rare words more (a word that appears in few documents is more informative). Good at exact terms like field names; blind to paraphrase.

Hybrid search runs keyword search and vector search, then merges the two ranked lists. Reciprocal Rank Fusion (RRF) merges by rank, not by score: each document gets 1 / (60 + rank) from each list and the sums are sorted. Using ranks avoids comparing BM25 scores with cosine scores, which are on unrelated scales. The constant 60 is the standard choice; it stops one list's top result from dominating.

8. Bi-encoders vs cross-encoders (reranking)

A bi-encoder (like MiniLM here) embeds the question and each candidate separately, then compares vectors. Fast, because candidates are embedded once. A cross-encoder reads the question and one candidate together and outputs a relevance score. Slower (one model call per pair) but usually more accurate. Reranking = retrieve many candidates with the fast bi-encoder, re-sort them with the cross-encoder. This project tested exactly that.

9. Fine-tuning and LoRA

Fine-tuning continues training a model on your task. Full fine-tuning updates all 1.5 billion weights: expensive. LoRA (low-rank adaptation) freezes the original weights and learns a small correction for chosen weight matrices: W + B·A, where A and B are thin matrices of rank r (here 16). Only A and B are trained, 10.55 million numbers here (0.68% of the model). The scale multiplies the correction's strength. The trained A and B are the adapter.

An epoch is one full pass over the training set. Iterations × effective batch size ÷ training examples = epochs.

10. MLX and Apple Silicon

MLX is Apple's machine-learning framework for M-series chips. mlx-lm runs and fine-tunes language models on it. All three Qwen arms use the same MLX stack, which matters: numbers produced on different software stacks aren't comparable (see "the confound" in Results).

11. Metrics for query generation

  • Execution accuracy (primary): run the generated query and the gold query; correct if the returned rows match.
  • CodeBLEU (secondary): text similarity to the reference, with syntax awareness. Rewards looking similar, not being right.
  • BERTScore (secondary): embedding similarity of the texts. Same weakness.

12. Metrics for retrieval rankings

  • recall@k: did at least one relevant item appear in the top k? Averaged over questions.
  • MRR@10 (mean reciprocal rank): 1 / the rank of the first relevant item (0 if none in the top 10), averaged.
  • nDCG@10: rewards putting the most relevant items highest, with graded relevance. Explained with a worked example in Statistics.

13. Paired comparisons

Two arms answer the same 304 questions, so their results are paired. Most questions come out the same both ways and say nothing about which arm is better. Only the discordant ones (right in one arm, wrong in the other) carry information. McNemar's test looks at exactly those. Full explanation in Statistics.

14. Pre-registration, positive controls, deviations

  • Pre-registration: write the hypothesis, the arms, the comparison and your prediction before running, and commit it. You can't then move the goalposts.
  • Positive control: check the measuring setup can reproduce a known result before trusting it on a new one (Azure vector search had to reproduce FAISS first).
  • Deviation: when reality departs from the plan, record it with a date before seeing the results it affects.

15. Goodhart's law

"When a measure becomes a target, it ceases to be a good measure." Here: optimising the ranking metric (nDCG) made it a worse predictor of whether answers were correct.

16. Cloud pieces (for the Azure arm)

  • Resource group: a folder for Azure resources. Deleting it deletes everything inside.
  • Azure AI Search: managed search service (keyword, vector, hybrid).
  • Azure OpenAI: hosted OpenAI models; you create a deployment of a model version and call it by name.
  • Container Apps: runs a container, scales to zero when idle. Container Registry (ACR) stores the image.
  • Key Vault: stores secrets. Managed identity: the app's own identity, so it can call other Azure services without any key in its settings; access is granted with role assignments (RBAC).
  • Application Insights / Log Analytics: traces and logs.
  • VNet, subnet, NAT Gateway, static public IP: a private network whose outbound traffic leaves from one fixed IP, so MongoDB Atlas can allow exactly that IP.

RAG, step by step (what build_prompts.py does for each question)

  1. Embed the question with MiniLM (rag/embed_utils.py): tokens → mean pooling → L2-normalise → 384 numbers.
  2. Search the FAISS index of the 1,213 pool questions for the 10 nearest (rag/data/fewshot.index, row-aligned with fewshot_metadata.json). Only the question text is embedded, never the query or schema: the job is "find past questions phrased like this one".
  3. Pick the database. vote (the default): the most common database among the 10 neighbours, ties broken by the nearest. rank1: just the nearest neighbour's database.
  4. Build the system prompt with build_system_prompt(): header → 10 example Q/query pairs → full schema of the picked database with FK annotations → a warning about string-typed numeric fields where relevant → 7 rules.
  5. Save everything per question to rag/data/rag_prompts*.json: the prompt, the retrieved ids, their cosine scores and whether the database was right.

Generation then reads those prompts and never touches retrieval again. That's why an Azure retrieval arm could be generated locally after the Azure search had done its part.

A subtlety worth knowing

Scoring runs each query against the gold database for that question, even if retrieval predicted a different one. A query written against the wrong schema almost always fails there, so a wrong database costs the case. The deployed service, by contrast, executes against the predicted database.

What counts as "the same rows" (results_match)

  1. Scalars (counts): plain equality.
  2. Lists: order is ignored, and dict key order is ignored (both are canonicalised and sorted).
  3. Key-tolerant fallback: if exact match fails, same number of rows and the same values per row with different key names still counts (for example {"max": 640} vs {"max_charge_amount": 640}). A null _id from $group is ignored; a real _id is compared.

Known ways this lets a wrong query through (measured by the false-positive audit): empty matches empty, a scalar matches by coincidence, order is never compared, and tiny collections make "top N" degenerate.

The safety guard (check_query_is_safe)

Model output is executed with eval(), so it's parsed first and rejected unless every piece is on an allowlist. It fails closed: anything it can't prove safe is refused.

  • Parse as a Python expression. A syntax error is a rejection.
  • Only the names db, None, True, False, len, sorted, list, dict.
  • Only these methods: find, find_one, aggregate, count_documents, distinct, sort, limit, skip, len, sorted, list, dict.
  • No attribute starting with _; no .client, .database, .collection (those reach other databases).
  • Arithmetic only + - /. Refusing **, *, %, << blocks CPU/memory bombs like 9**9**9.
  • $where, $function, $accumulator, $merge, $out refused anywhere, at any depth. Dict keys must be literal strings (so "$o"+"ut" tricks fail), with no ** unpacking and no dict() call.
  • Aggregation stages must be on a read-only list ($match, $project, $group, $lookup, $unwind, $facet, $unionWith, $setWindowFields, …).

The statistics, worked by hand

1. Why paired, and McNemar's test

Two arms answer the same 304 questions. Put every question in a 2×2 table:

New arm rightNew arm wrong
Old arm righta: both right (no information)b: lost
Old arm wrongc: gainedd: both wrong (no information)

Cells a and d say nothing about which arm is better; they came out the same. Only b and c (the discordant pairs) matter. If the two arms were really equally good, each discordant question would be equally likely to fall either way, like a fair coin. So under the "no difference" hypothesis, c out of (b + c) follows a Binomial(b + c, ½) distribution.

The p-value is the chance of a split at least as lopsided as the one observed, in either direction, if the coin were fair. "Exact" means computing that binomial probability directly rather than using the chi-square approximation, which is unreliable when b + c is small.

Worked example: rank-1 (gained 6, lost 0)

b + c = 6. The chance all 6 land on one given side is (½)6 = 1/64. Two-sided (either side all-6): 2 × 1/64 = 0.03125. That's the published p = 0.031. Six questions, no losses, and it's only just significant, because 6 flips is very little evidence.

Worked example: reranking (gained 20, lost 22)

42 discordant, split 20/22: close to what a fair coin gives. p = 0.88. Reranking changed 42 answers and it was churn, not improvement.

2. Why not just compare the two accuracies?

One accuracy on 304 questions has an uncertainty of about ± 5.6 points (95%, at ~47%): 1.96 × √(0.47 × 0.53 / 304) ≈ 0.056. Treated as two independent numbers, two arms would need to differ by roughly 11 points before you could call it. Pairing removes the shared questions, so a 3-point change touching a handful of cases can still show up. That's also why a fixed rule like "fail if accuracy drops 2 points" is wrong both ways: it fires on noise and stays silent on a real change hidden in a large swap.

3. A p-value is not the effect size

Always report net change and discordant counts next to p. gpt-4o's p = 6.8 × 10⁻¹⁰ says "certainly not chance"; the +55 cases says how much. Rank-1's p = 0.031 is marginal, yet it lost zero cases, and the mechanism is understood. Both facts matter.

4. Noise floors: how small a difference can be real

  • The oracle itself: one case in 277 flipped with a byte-identical query (a $sort + $limit 1 over a tie; MongoDB may return either row). About 0.4%.
  • Qwen on MLX: fully deterministic (identical per-token log-probabilities across runs).
  • gpt-4o at T = 0: not deterministic. Three runs of 50 cases differed in 3–6 queries per pair and 0–2 correctness flips, with identical totals. Report it as "~198 ± a few".
  • bf16 cascade: a tiny floating-point difference early in greedy decoding can change the whole rest of an answer. Why "fused vs adapter" text matched only 90% in FORGE even though the maths is identical.

5. Correlation: how much ranking explains

Per question, nDCG@10 vs correct/incorrect: r = 0.307. Squared, r² = 0.094, so ranking quality explains about 9.4% of the variation in whether an answer is right; the rest is the generator. The correlation is real (t = 5.61 on 302 degrees of freedom, p = 4.7 × 10⁻⁸) but small. And the best-ranked arm had the weakest link (r = 0.200): Goodhart's law, observed.

6. Ranking metrics, worked

Say a question's top 4 retrieved examples have graded relevance [3, 0, 2, 1] (best first).

  • DCG@4 = Σ (2g − 1) / log₂(i + 2) = 7/1 + 0/1.585 + 3/2 + 1/2.322 = 7 + 0 + 1.5 + 0.431 = 8.931
  • Ideal order [3, 2, 1, 0]: 7/1 + 3/1.585 + 1/2 + 0 = 9.393
  • nDCG@4 = 8.931 / 9.393 = 0.951. 1.0 would be a perfect order. The ideal here is the best order of what was retrieved: nDCG judges ordering; recall judges what got retrieved at all.

With binary relevance [0, 0, 1, 0, 1]: reciprocal rank = 1/3 (first relevant item at rank 3); recall@1 = 0, recall@3 = 1. MRR averages the reciprocal ranks over all questions. These functions are in rag/metrics_retrieval.py, with hand-computed tests in tests/test_metrics_retrieval.py.

7. Soft voting and temperature (the vote-weighting analysis)

Score each database by Σ exp(similarity / τ) over the neighbours. As τ → ∞, every neighbour counts 1 (the plain vote). As τ → 0, only the nearest counts (rank-1). Sweeping τ showed accuracy rises steadily as τ shrinks: no middle setting beats rank-1 by more than one case. Plain similarity-sum was worse than counting (256 vs 258), because any sum over neighbours inherits the pool-frequency bias.

8. Pre-registration and gates in practice

  • Azure retrieval: prediction ≥ 155 (wrong: 148); bar ≥ +9 and p < 0.05 (not met). Gate 1 ≥ 300/304 (missed at 298: all 6 mismatches were one tied pair of identical questions; the deviation was logged in commit af3d073 before any hybrid number existed).
  • gpt-4o: prediction 147–150 (far too low: 198).
  • gpt-4o + rank-1: prediction 200+ (correct: 212).

Reporting the misses is the point: a prediction that can't be wrong isn't a prediction.

9. Several comparisons at once

Every extra arm is another chance of a fluke "significant" result. At α = 0.05, one test in twenty is significant by luck. The protection here is pre-registering the primary comparison per experiment, and reading secondary comparisons as supporting, not as separate discoveries. (Formal corrections like Holm's method are covered in the ARBITER guide.)

2. The confound, and the reversed conclusion ⭐

Originally, baseline and RAG ran on Google Colab (Hugging Face transformers, fp16, shared GPU) while fine-tuning ran on the Mac (MLX, bf16). Re-running RAG on MLX, the same 61 questions, same gold, same scorer went from 24.6% to 50.8%. Cause, found by testing rather than assumed: fp16 GPU inference without deterministic flags isn't bit-identical across Colab sessions. A prompt change and its exact revert, run back-to-back in one session, gave byte-identical output, so the earlier swing came from the session boundary, not the code. The earlier headline, "fine-tuning beats RAG", was reversed and published as reversed. This is the origin of the house rule: change one variable at a time.

3. Smaller findings on the Qwen arms

  • FK annotations: 142 with vs 141 without. A null result; they neither help nor hurt.
  • Epoch-parity bug: the 23-database adapter first trained for 200 iterations (0.73 epochs): 73/304 (24.0%). At 1000 iterations (3.67 epochs, matching the first adapter): 103/304 (33.9%).
  • Batch collision bug: putting college_1/2/3 in one training batch taught the model to mix their field names. Separating near-identical databases took college_3 from 0% to double digits.
  • Fine-tuning's false positives are 4× RAG's (next section): LoRA learns the shape of a correct query, so it writes plausible pipelines with wrong filters. That's exactly the failure a row comparison can miss.

4. Is the gold right? Is the scorer right?

  • SQL cross-check (evaluation/crosscheck_sql_gold.py): the hand-written Mongo gold was checked against Spider's own SQL on Spider's SQLite. Of 1,409 cases that run on both sides, 1,264 agree (89.7%); 87.2% on the test slice. Most disagreements are not gold errors: text-typed numbers (38), ties at the top of ORDER BY … LIMIT 1 (37), aggregates over text (12). The tie class means some questions have more than one right answer, which caps measurable accuracy for every arm.
  • Gold health: 0 of 1,517 gold queries fail to run; 4 return empty (all flight_2).
  • False-positive audit (evaluation/audit_false_positives.py): wrong queries scored correct. Baseline 2 of 15, RAG 3 (2.1% of its correct answers), fine-tuned 9 (8.7%). Corrected: RAG 138, fine-tuned 94. The gap between them widens, from 12.8 to about 15.4 points.

7. Rank-1: the change that worked ⭐

Database from the nearest neighbour instead of a vote: database accuracy 258 → 275/304; execution 143 → 149, gained 6, lost 0, p = 0.031. Only 27 prompts changed (those where the database changed). Mechanism: an unweighted vote counts neighbours, and for near-identical sibling databases the count follows how often each appears in the pool, not how close it is. chinook_1 (33 pool examples) lost all 9 of its test questions to store_1 (84). Precision beat volume: reranking rewrote 300 prompts and did nothing; rank-1 touched 27 and every flip went the right way.

8. Azure hybrid retrieval: a null result ⭐

Azure AI Search, BM25 + vector fused by RRF, everything else fixed (Qwen on MLX). Better retrieval: recall@5 0.964 → 0.974, MRR 0.929 → 0.939, database vote 258 → 263. Execution 143 → 148, 19 / 14, p = 0.49; the pre-registered bar (+9 and p < 0.05) was not met, and the prediction (≥ 155) was wrong. 26 of the 33 flips had the same database and schema, so they're example churn again. One of the 19 gains is a false positive (store_1-25: sorted by hire date instead of birth date, and happened to return the same single row). Takeaway: Azure Search is a free choice on operational grounds, not an accuracy improvement.

9. The generator is the big lever ⭐

gpt-4o on the byte-identical prompts: 198/304 (+55; 69 / 14; p = 6.8 × 10⁻¹⁰), about ten times any retrieval change. The whole gain is in questions where retrieval picked the right database (136 → 192 of 258); with the wrong schema, gpt-4o does no better than Qwen (6 vs 7). So the database decision becomes the constraint: 38% of gpt-4o's remaining failures.

gpt-4o + rank-1: 212/304 (69.7%), +14 over gpt-4o with the vote (17 / 3, p = 0.0026). On the 20 cases rank-1 fixes, Qwen gained 5 and gpt-4o gained 12: a retrieval policy's value depends on the generator behind it. The other 277 prompts were byte-identical between those two runs, which isolates gpt-4o's own noise at about ±2.

Cost: about $0.005 per query (≈ $1.55 per 304-case run); all gpt-4o work ≈ $3.64. Caveats to volunteer: one run per arm; gains not audited for false positives; gpt-4o may have seen Spider in training (this compares two systems on this benchmark, not generalisation).

Interview: test yourself

Say your answer out loud first, then open the question.

Walk me through the project in 60 seconds.

A benchmark for natural language to MongoDB. 1,517 hand-verified pairs across 23 databases: 1,213 as a retrieval pool, 304 held out. Every generated query is graded by running it on a live Atlas cluster and comparing rows. Zero-shot 4.9%, fine-tuned 33.9%, RAG 46.7%. Rank-1 database selection took RAG to 49%. On Azure, swapping the generator to gpt-4o with everything else fixed took it to 65%, and 69.7% with rank-1. That's the configuration a FastAPI service on Container Apps serves.

Why execution accuracy instead of BLEU or exact match?

Text similarity is wrong both ways: a correct query in a different shape scores low, and a subtly wrong one that looks right scores high. My own data shows it: RAG and fine-tuning are within 0.0024 on CodeBLEU but 12.8 points apart on execution. Then I checked the oracle itself: gold against Spider's SQL (89.7% agreement, disagreements classified), and a false-positive audit of "correct" answers.

Tell me about a time you were wrong.

The confound. My headline was "fine-tuning beats RAG". Baseline and RAG ran on Colab in fp16, fine-tuning on the Mac. Re-run on one stack, RAG on the same 61 questions went 24.6% → 50.8%. I proved the cause (a prompt change and its revert gave identical output within one session, so the swing was the session boundary), reversed the conclusion and published the reversal. Since then: one variable per experiment.

Would you add a reranker?

Only if it moves the task metric, and mine didn't. A cross-encoder improved recall@5 0.964 → 0.984 and nDCG, and execution went nowhere: 20 gained, 22 lost, McNemar p = 0.88. Recall@10 was already 0.987, so there was nothing to find. nDCG explained only 9.4% of correctness, and the best-ranked arm correlated worst. Measure end to end.

What did work in retrieval?

Rank-1 database selection: +6, zero losses, p = 0.031. The vote counted neighbours, so sibling databases were decided by how common they were in the pool, not by how close. It touched 27 prompts; reranking touched 300. Precision beat volume. And with gpt-4o behind it, the same fix was worth +12 instead of +5.

Explain McNemar's test on a whiteboard.

Same questions, two arms. Draw the 2×2. Both-right and both-wrong say nothing. Under no difference, each discordant question is a fair coin, so gained out of (gained + lost) is Binomial(n, ½). The p-value is the chance of a split at least that lopsided, both sides. Exact because the counts are small. Example: 6–0 gives 2 × (½)⁶ = 0.031.

Why was the Azure vector search run at all, if FAISS worked?

As a positive control. Before believing a hybrid result, the harness had to reproduce a known one: exact cosine on the same vectors should match FAISS. It matched on 298/304 with a pre-registered bar of 300. All six misses were one tied pair of identical questions, so I logged a dated deviation before any hybrid number existed, and reported the gate as missed.

Did Azure hybrid search improve accuracy?

No: 148 vs 143, p = 0.49, 19 gained / 14 lost. Every ranking metric improved, but 26 of the 33 flips had the same database, so it was example churn. It's an infrastructure choice for the service, not an accuracy gain.

How is gpt-4o's number not just contamination?

It might be partly: Spider is public, so gpt-4o may have seen it. I say that up front. The result compares two systems on this benchmark; it isn't evidence about unseen schemas. The structural finding holds either way: with the wrong schema, gpt-4o does no better than Qwen (6 vs 7).

Your endpoint runs eval() on model output. Convince me it's safe.

Layers. An AST allowlist before every eval (names, methods, read-only stages, no $where/$out/$merge at any depth, literal keys only, no .client back-references, no ** bombs), with no builtins in the eval. A database allowlist that fails closed. A read-only Atlas user reachable only from one NAT IP. Ingress limited to one IP, an API key, a 500-character limit, rate limiting, 50-row cap, hashed logs. The one I'd trust least alone is the allowlist; that's why it isn't alone.

Why a NAT Gateway?

A consumption-only Container Apps environment leaves from a shared pool of about 190 IPs used by other tenants. Allowlisting that in Atlas would admit any app in the region. A NAT Gateway on the app's subnet gives one static IP only this app uses. Cost: about $1/day.

Cold starts are 34 seconds. Acceptable?

For a demo, yes. Scale-to-zero is free when idle; min-replicas 1 removes the cold start but pays around the clock. The cold start is almost all container start (a ~1 GB image with CPU torch); the pipeline is ~2.5 s of it. The cheaper fix is a torch-free (ONNX) embedder to shrink the image.

Why did fine-tuning lose to RAG?

After fixing an under-training bug it reached 33.9% vs RAG's 46.7%. Fine-tuning teaches the shape of correct queries, which also produces plausible-but-wrong filters: its false-positive rate is 4× RAG's. RAG shows the model real, similar, correct examples every time. And they fail on different questions: the union is 59%.

Deep-dive risk: know the detail behind these lines

  • "1,517 cases": the dataset. The oracle grades 304. Never say "1,517-case benchmark asserted by an oracle".
  • 142 vs 143: same RAG run; the aggregate says 142, the re-scored case file 143. One case of oracle noise.
  • 0.68% trainable: all seven projection matrices in the last 16 of 28 blocks, rank 16.
  • ~198 for gpt-4o: not bit-reproducible; 0–2 flips per 50 cases.

Do not say

  • "LoRA outperformed every RAG configuration": reversed.
  • "4.9% → 24.6%" or "32.8%": stale, from the confounded setup.
  • "Azure Search improved accuracy": it didn't.
  • "Production": the service is a deployed demo behind an IP allowlist, with no real users.
