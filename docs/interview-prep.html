00The project in 90 seconds

Take a 1.5-billion-parameter open model you can run on a laptop and ask it to do something a frontier API model does easily: turn an English question into a working PyMongo query against a real database it has never seen. Out of the box it manages 4.9%. The question the project answers is which adaptation strategy closes that gap, and by how much, measured honestly.

Two strategies are compared head to head under everything-else-held-constant conditions:

Arm 2 · retrieval

RAG

Don't touch the weights. At query time, retrieve the 10 most semantically similar solved examples from a 1,213-case pool, predict which database the question is about by majority vote over those neighbours, and paste that database's full schema plus the ten worked examples into the prompt.

46.7% — 142/304.

Arm 3 · adaptation

LoRA fine-tuning

Change the weights, cheaply. Train rank-16 low-rank adapters over 16 layers — 10.55M trainable parameters, 0.68% of the model — on 1,091 examples drawn from the same pool, so the task format and the schemas live in the weights rather than in the prompt.

33.9% — 103/304.

Every number above comes from actually executing the generated query against MongoDB Atlas and comparing the returned documents to gold output. Nothing in this project is scored by string similarity, and that decision is the spine of the whole thing — see CodeBLEU & BERTScore for what happens when you do score by string similarity instead (the two arms become indistinguishable).

Headline finding

Retrieval beats fine-tuning on this task, by 12.8 points — and the margin widens to ~15.4 once you audit which "correct" answers are actually correct. Fine-tuning's false-positive rate is 4× RAG's (8.7% vs 2.1% of its correct set), which is exactly what the mechanism predicts: LoRA teaches the shape of a valid pipeline, so the model emits structurally plausible queries with the wrong predicate inside — the one failure mode result-comparison is blind to.

The second finding is a methodology finding, and it is the one worth leading with in an interview, because it involves publicly reversing a conclusion the project had already reported:

The conclusion that got reversed

An earlier round of this project concluded "LoRA fine-tuning beats RAG at every K tested." That conclusion was an artefact of the serving stack, not the method. Baseline and RAG were being generated in Colab with HuggingFace transformers in fp16; fine-tuning was generated locally with MLX-LM in bf16. Re-running RAG on the same MLX-LM stack, on the identical 61 questions with identical gold and identical scoring code, moved it from 24.6% to 50.8%. Nothing but the runtime changed. See the serving-stack confound.

The five things this project must answer cold

QuestionAnswer
Why execution accuracy and not BLEU / exact match? Because a query is correct if it returns the right rows, and there are many textually different queries that do. The repo has the receipt: RAG and fine-tuning score 0.2783 vs 0.2759 on CodeBLEU — a 0.0024 gap — while separating by 12.8 points on execution accuracy. String metrics cannot see the thing that matters.
Which won, and why does the mechanism explain it? RAG, 46.7% vs 33.9%. The task's hard part is grounding — knowing that this database calls the column Horsepower and stores it as a string. Retrieval injects exactly the right grounding at query time for the specific question; LoRA has to compress 23 databases' worth of grounding into 10.55M parameters and then recall it unprompted. Retrieval also degrades gracefully: it is wrong about the database on 15% of cases and still recovers.
How do you know your gold answers are right? Cross-checked against Spider's own gold SQL, executed on Spider's original SQLite files: 1,264 of 1,409 (89.7%) agree on a value-based comparison, zero SQL errors, and the 145 disagreements are auto-classified — most are SQLite type coercion or genuinely under-determined questions, not gold defects.
How do you know your scorer is right? A dedicated false-positive audit, because result-comparison admits four specific classes of wrong-but-passing query. 14 confirmed false positives and 10 false negatives across 114 flagged candidates, with verdicts keyed by (arm, id), not by case — a false positive is a property of a generated query, not of a test case.
What broke, and what did you learn from it? A silent SIGSEGV from three copies of libomp in one venv; a 0.75-epoch under-training bug hidden behind a "held constant" hyperparameter; a naming-collision leak between college_1/2/3; a $where JavaScript injection hole in the eval guard found by writing the first test; and results files committed next to prompts that did not produce them. Every one of those is now either fixed or documented in-repo.

—Concept glossary

Every idea this project rests on, defined the way you would want to define it out loud, with the project's own instance of it attached.

The task

Text-to-Querysemantic parsing

Mapping a natural-language question to an executable query in a formal language. The classic form is Text-to-SQL; this project does Text-to-PyMongo, which is strictly harder in two ways: MongoDB has no declared schema and no declared foreign keys, and the target is a Python expression embedding a JSON-shaped aggregation pipeline rather than a flat declarative sentence.

Spiderthe benchmark

A large-scale, cross-domain Text-to-SQL dataset: ~200 databases with multiple tables, human-written questions, and gold SQL. Its defining property is cross-database generalisation — the test databases are unseen at train time, so a model cannot memorise one schema. This project takes 23 Spider databases, converts them to MongoDB, and hand-writes PyMongo gold for 1,517 of the questions.

Schema linkingthe actual hard part

Deciding which tables/collections and which columns/fields a question refers to. It is where most Text-to-Query systems fail, and this project's baseline row proves it: 172 of 304 baseline queries ran cleanly and returned nothing — perfectly formed queries against invented names. Both adapted arms are, fundamentally, two different ways of solving schema linking.

Execution accuracythe primary metric

Run the generated query against the real database, run the gold query too, compare the returned result sets. Binary per case. The alternative, exact-match accuracy, compares query strings and is badly broken for this task because many textually different queries are semantically identical. Execution accuracy's own weakness is the mirror image: many semantically different queries return the same result — the false-positive problem this project audits explicitly.

Retrieval

RAGretrieval-augmented generation

Instead of relying on parametric knowledge, fetch relevant context at inference time and put it in the prompt. Here it is used for two distinct jobs at once: retrieving worked examples (in-context learning) and retrieving the right schema (grounding). The second is doing most of the work.

Dense retrievalvs. lexical / BM25

Encode query and documents into a shared vector space with a neural encoder, rank by vector similarity. Catches paraphrase where BM25 (term overlap) cannot — and questions here are paraphrases of each other ("What is the horsepower of the car with the greatest accelerate?" vs "...with the largest accelerate?"). No lexical or hybrid baseline was run, which is an honest gap.

Bi-encoder & mean poolingall-MiniLM-L6-v2

Query and document are embedded independently by the same encoder, so all 1,213 document vectors can be precomputed. Sentence embeddings come from attention-mask-weighted mean pooling over token hidden states — not the CLS token, because this checkpoint was contrastively trained with mean pooling. The mask matters: a plain .mean(1) would dilute short questions with padding, and since padding is to the batch maximum, a question's vector would depend on what else happened to be in its batch.

Cosine via inner productthe L2-normalise trick

cos(a,b) = a·b / (‖a‖‖b‖). Normalise every vector to unit length and the inner product is the cosine. That is why embed() ends with F.normalize(vecs, p=2, dim=1) and the index is IndexFlatIP. Skip the normalisation and the ranking silently becomes a magnitude-biased dot product that favours long questions — no error, just worse neighbours.

FAISS IndexFlatIPexact, not approximate

Brute-force scan of all 1,213 vectors, exact top-K, no training step. ANN indexes (IVF, HNSW) exist to avoid scanning millions of vectors; at 1,213 × 384 floats = 1.86 MB a full scan is sub-millisecond. IVF would additionally be under-trained by construction — FAISS wants roughly 39×nlist training points. Choosing exact search here is right-sizing, and being able to say why is worth more than having used the fancier index.

In-context learningfew-shot prompting

The model adapts to a task from examples in the prompt, with no weight update. The K=3→5→10 sweep on the earlier 61-case slice rose monotonically (21.3% → 22.9% → 24.6%), which is why K=10 is the canonical setting.

Adaptation

PEFTparameter-efficient fine-tuning

Adapt a large model by training a small number of new or selected parameters. The family includes adapters, prefix/prompt tuning, BitFit, IA³ and LoRA. The shared motivation is that optimizer state, not weights, dominates fine-tuning memory: AdamW carries two fp32 moments per trainable parameter.

LoRAlow-rank adaptation

Freeze W, learn ΔW = BA with rank r ≪ d, apply as y = Wx + (α/r)·BAx. Rests on the hypothesis that the update needed for a narrow task has low intrinsic rank even when W does not. Here: r=16, α=32, 16 of 28 layers, 7 modules per layer, 10.55M params = 0.684%.

Catastrophic forgettingwhy LoRA is also a regulariser

Full fine-tuning on ~1,000 examples would overwrite general capability. The rank bottleneck limits how much of the pretrained function can be modified at all — the constraint is the regularisation. This is why dropout: 0.0 is defensible here even though it is undefended in the config.

GQAgrouped-query attention

Multiple query heads share one key/value head, shrinking the KV cache. Visible directly in this project's adapter shapes: k_proj/v_proj LoRA-B matrices are [16, 256] while q_proj/o_proj are [16, 1536] — 12 query heads, 2 KV heads, head_dim 128, so 2×128 = 256.

Gradient checkpointingthe OOM fix

Discard intermediate activations on the forward pass and recompute them during the backward pass. Trades compute for memory precisely where the pressure is. Combined with batch_size 2 × grad_accumulation 2, it is what let effective-batch-4 training fit in 24 GB unified memory. Note the diagnostic detail: the OOM appeared only on the first backward pass — the validation forward pass had already succeeded at loss 1.664 — which is exactly the signature of a backprop-memory problem rather than a model-load problem.

Epoch vs. iterationthe bug that cost 9.9 points

An iteration is one optimizer weight update. An epoch is one full pass over the training set. examples_seen = iters × batch × accum; epochs = examples_seen / |train|. Holding iters fixed across a 5× larger corpus divides epoch coverage by 5. See the epoch-parity fix.

Confidence and evaluation

Token log-probabilitythe default confidence signal

The model's own log P(token | context) at each step. Mean logprob is length-normalised and is what calibration work uses; sum logprob is the true sequence log-likelihood and penalises long answers. The two rank candidates differently, so both are persisted. Measured here: correct RAG generations average −0.026 vs −0.065 for incorrect — real but weak.

Self-consistencythe stronger signal

Sample k generations at T > 0 and report the fraction agreeing with the modal answer. Introduced for chain-of-thought reasoning; used here as a confidence estimate. Critically, agreement is decided on AST-canonical form, not raw strings — otherwise the number measures formatting, and two identical queries differing only in quote style would split the vote. Measured: 81.5% accuracy at unanimous agreement vs 22.4% below 0.6.

Calibration & ECEwhat the signals enable

A model is calibrated if, among predictions it assigns 70% confidence, ~70% are correct. Expected Calibration Error bins predictions by confidence and averages |accuracy − confidence| per bin. No ECE is computed in this repo — but the raw per-token logprob vectors and all 1,520 self-consistency samples are persisted specifically so it can be, without regenerating anything.

Selective predictionthe obvious next build

Answer only above a confidence threshold; abstain or escalate below it, trading coverage for accuracy. The self-consistency buckets above are exactly a coverage/accuracy curve: keep the 54 unanimous cases and you get 81.5% at 18% coverage.

CodeBLEUsecondary metric

Four components: n-gram BLEU, keyword-weighted n-gram BLEU, AST sub-tree syntax match, and data-flow graph match. Designed for multi-statement code. See why the fourth component is excluded here — there is a real bug in the composite as well as a task mismatch.

BERTScoresecondary metric

Greedy-matched token-level cosine similarity between contextual embeddings of candidate and reference (roberta-large, a middle layer). rescale_with_baseline=True applies a monotone affine rescale against random-sentence-pair baselines, so unrelated text maps to ~0 instead of ~0.85. Being affine and monotone it cannot change a ranking — it only makes differences readable.

Characterization testthe testing idea worth stealing

A test that pins current behaviour, including behaviour you believe is wrong, so that changing it becomes a visible, deliberate assertion flip rather than a silent regression. Four tests here assert that specific wrong queries currently score correct, each cross-referenced to a confirmed case id in the false-positive audit.

MongoDB, specifically

Aggregation pipelineMongo's query language for real work

An ordered array of stages, each transforming a document stream: $match (WHERE), $group (GROUP BY), $sort, $limit, $project (SELECT), $lookup (LEFT JOIN), $unwind (flatten an array), $facet (run sub-pipelines in parallel over the same input), $addFields, $expr (use aggregation expressions inside a match).

$lookupa join, with caveats

Left outer join by localField/foreignField, producing an array field that usually needs $unwind. Two traps this project hits constantly: it does not coerce types the way SQL does, so joining str to int silently matches nothing; and reversing the join direction is often a genuine semantic equivalence, which is why 9 of 18 accepted audit cases are reversed joins.

$facet for set operationsno EXCEPT / INTERSECT

MongoDB has no direct EXCEPT/INTERSECT. The gold queries express them by running two sub-pipelines in a $facet and comparing the arrays — which is why the SQL cross-check has to flatten a one-document-holding-an-array shape against SQL's N separate rows.

The string-typed-numeric trapinherited from SQLite, not invented

SQLite is dynamically typed per value. A column declared INTEGER can hold the text '150' or the text 'null'. The row-by-row conversion to Mongo faithfully preserves that, so cars_data.Horsepower is a string in Mongo. Consequences: {"$gt": 150} on a string matches nothing; "11" > "9" is False as strings; and $toDouble("null") throws a server error that fails the whole query. This single data property drives a prompt note, a schema-card annotation, a bad_type_cast bug-taxonomy bucket, and 50 of the 145 gold cross-check disagreements.

$wherethe security hole that mattered

A query operator that executes arbitrary JavaScript server-side in the mongod process. Together with $function and $accumulator it is the code-execution surface; $out and $merge are the write surface. All five are in FORBIDDEN_OPERATORS — added after writing the first test suite found that $where inside a find() filter passed the guard.

Dependency landmine — and the best "debugging" story you own

Three packages each vendor their own copy of libomp.dylib: torch/lib/, faiss/.dylibs/, sklearn/.dylibs/. On macOS the dynamic loader binds the first copy loaded, process-wide. If faiss's copy wins, the first torch forward pass SIGSEGVs the interpreter — exit 139, no traceback, nothing catchable.

Reproduced minimally in both directions: import faiss then torch → crash on the first model(**enc); import torch then faiss → clean run, correct results. rag/build_prompts.py imported faiss first because that is alphabetical order, so step 3 of the README's own reproduction recipe died silently right after printing Embedder ready., before a single prompt was built.

Fixed by pinning import order, with a blank line, a # noqa: E402, and an explicit comment telling isort not to merge them back. The second-order damage is the real lesson: the crash did not just fail a run — it left rag_prompts.json stale relative to the results committed beside it. A silent crash became a reproducibility corruption, and that is part of what motivated the manifest system.

And the honest weakness in that fix

The import-order invariant is enforced by convention at each call site. It was fixed in rag/build_prompts.py and rag/build_retrieval_index.py, and then recurred in demo_ui/live_inference.py — which imports faiss directly rather than going through build_prompts, so it never inherited the fix. There it took down the whole Streamlit process at the first embed() call, and because a SIGSEGV is not a Python exception, the app's broad except Exception could never have caught it. The right fix is a single import-ordering shim module that every entry point imports first. That is the "what would you do differently" answer.

1Spider → SQLite → MongoDB Atlas

The conversion, and what it deliberately does not do

sqlite_to_mongo.py is 54 lines and the semantics matter more than the code: one table → one collection, one row → one flat document, verbatim.

conn.row_factory = sqlite3.Row
tables = cursor.execute("SELECT name FROM sqlite_master WHERE type='table';").fetchall()
for (table,) in tables:
    if table == "sqlite_sequence":
        continue  # internal SQLite bookkeeping, not real data
    rows = cursor.execute(f"SELECT * FROM {table}").fetchall()
    json.dump([dict(row) for row in rows], f, indent=2)
No FK dereferencingthe load-bearing decision

Nothing embeds, denormalises, or pre-joins. Relational structure is preserved as separate collections holding the same scalar key columns, so a SQL JOIN must become an explicit $lookup that the model writes. That keeps the benchmark honest — the model is not handed a pre-joined document. FK knowledge is re-introduced later only as prompt metadata, never as a data transformation.

No type coercionwhy the string-typed-numeric trap exists

dict(sqlite3.Row) uses SQLite's own storage classes. Because SQLite is dynamically typed per value, a column declared INTEGER holding the text '150' arrives in Mongo as a Python str. The type mismatches were not introduced by the model or the prompt — they are faithfully inherited from Spider's source data, and the pipeline chose to surface them rather than silently coerce them. That is a strong answer to "isn't your data dirty?"

No _id writtenwhy prompt rule 5 exists

Mongo assigns an ObjectId at insert. It is not part of the schema, is non-deterministic, and will break an exact result comparison — hence the prompt rule telling the model to project it away, and hence ONLY_ID_DIFFERS being the dominant false-negative class.

A footgun caught and documented

sqlite3.connect() does not error on a missing file — it silently creates a new empty database there. Without an explicit existence check, a typo'd db name or a wrong working directory produces a perfect silent no-op: no tables, zero JSON files written, and no error saying why. The script raises FileNotFoundError first.

The reverse direction, and why it is sampled

dump_atlas_to_local.py exports Atlas → local JSON for field-type inference only, capped at 5,000 documents per collection by default:

cursor = client[db_name][coll_name].find({}, {"_id": 0})   # _id is not schema
if sample_cap:
    cursor = cursor.limit(sample_cap)
out_path.write_text(json.dumps(list(cursor), indent=2, default=str))

The justification is exact: "A representative sample is exactly as good as a full dump for inferring 'what type is this field'" — and gold-query execution always runs against live Atlas anyway. It keeps wta_1.rankings (510,437 rows) cheap. default=str is the BSON escape hatch at dump time. Per-collection and per-database try/except with an error counter means one bad database cannot abort a 23-database run.

Root cause, not another symptom

rag/schema_cards.py once held a hand-maintained dict of 6 databases. It drifted twice: round 2 added 7 databases without a committed update (the evidence is a stale schema_cards.json on disk listing 13 — someone expanded it locally and never committed), and round 3 added 10 more with the dict still at 6. The fix was not to patch it a third time: _discover_collections() now globs database/mongodb/*/*.json at import. The script header says it plainly — "there is no dict left to drift out of sync."

2The split, and leakage

1,517 gold cases → 1,213-case few-shot pool + 304-case held-out test set. The pool is what RAG retrieves from and what LoRA trains on, so the two arms consume identical information. The test set is touched by nothing but scoring.

fewshot_pool, test_set = train_test_split(
    cases, test_size=0.2, stratify=databases, random_state=42,
)
Stratified by database onlynot database × complexity

23 databases × 3 complexity levels = 69 cells over 1,517 cases. sklearn raises when a stratum is too small, and a 2-member cell cannot be split 80/20 at all — it would be "stratification in name only." Resulting test distribution runs from college_1: 32 down to wta_1: 6, proportional throughout.

A fraction, not a fixed counta migration hazard, pre-empted

TEST_FRACTION = 0.2 is a proportion on purpose. The split was originally 100/21 (~17%) when the corpus was 121 cases; a hardcoded TEST_SIZE = 21 left over from that era would have silently stopped being an 80/20 split as the corpus grew.

A fixed seed, changed deliberatelyanti seed-hacking

The comment is one sentence and it is the whole point: "change RANDOM_STATE deliberately, not by re-running until you like the numbers." That is a written guard against researcher degrees of freedom.

Additive, not reshuffledacross three expansion rounds

Each expansion round added to the existing split rather than re-splitting from scratch. Re-splitting would have moved cases the model had already effectively seen into the test set, and every prior round's result would have become incomparable.

Leakage assertions — asserted, not trusted

overlap = fewshot_ids & test_ids

The comment explains why this is asserted even though train_test_split partitions rather than samples with replacement:

The two length assertions catch a different bug from the overlap check: duplicate ids in the source corpus. And str(c["id"]) coercion matters because ids are genuinely mixed-type across expansion rounds — integers (1), short codes (car-h3, cs-e8), and Spider-derived (spider-car_1-39).

The fine-tuning prep adds a third, stronger check — exact question-text overlap — which catches the same question assigned two different ids, a leak that disjoint id sets would miss entirely. Both were re-verified independently for this document: 0 id overlap, 0 question overlap.

Type inference — first non-null, not docs[0]

A small fix with a real consequence

Field order is fixed from docs[0] for stable prompt output, but the resolved type scans every document and latches the first non-None value's type, tracking a nullable flag separately. The motivating case: world_1.country.IndepYear is a real integer field, null for 47 of 239 countries, and docs[0] happens to be one of the null ones. Trusting docs[0] alone labelled a genuine integer column NoneType in the LLM-facing schema prompt — actively misleading, worse than omitting the field. Fields null in every document are marked "unknown, nullable" rather than guessed.

The general point: schema inference from a document store is genuinely ambiguous, because there is no DDL. Sampling one document is the naive approach and it produces wrong answers on exactly the columns that matter.

FK edges — mined from the gold queries

MongoDB has no declared foreign keys, so the join graph had to come from somewhere. It was derived by parsing every $lookup stage's from/localField/ foreignField triple out of the 305-case gold corpus, keeping only canonical edges — intermediate field names created by aggregation workarounds ("CountryInt", "sid_int") are replaced with the real schema field name.

22 edges across 6 databases. Three carry an explicit type warning: concert.Stadium_ID, singer_in_concert.Singer_ID, car_makers.Country — all str → int, use $toInt.

Stated limitation, and it bounds a result

FK edges cover only the original 6 of 23 databases; extending them is open work, and the code says so. This directly bounds the FK A/B test's possible effect size — 17 of 23 databases render identically in both variants, which makes them a free implicit no-op control, and makes the observed 1-case difference exactly what you would predict.

The clean-clone fallback

database/ is gitignored because it holds the Atlas dumps. So on a fresh clone _discover_collections() found nothing, build_cards() returned [], and the baseline arm silently built a schema-free prompt — making it "the one thing in this repo not reproducible from a fresh checkout."

Why this class of bug is the worst kind

The pipeline completes. It produces plausible numbers. And the numbers are for a different experiment than you think you ran. There is no error to notice, no exception to catch, and no smell in the output. Failing loudly is not a nicety here — it is the only way this bug is ever detectable.

Two naming quirks worth knowing cold

model_list.jsonappears in five places

car_1 has a collection whose name literally contains .json. Path.stem would strip it as a file extension and get the name wrong. It is special-cased in the schema-card overrides, the Atlas dumper's filename builder, the loader, and — user-facing — prompt rule 2: "use db['model_list.json'] for that one collection", because dot-attribute access cannot express a name containing a dot.

An empty collection is a missing collectionverification semantics

atlas_verify_and_load.py treats a collection that exists with 0 documents as missing, because an empty collection fails a query exactly like a missing one — it returns an empty cursor, not an error. Ignoring it would reproduce the original bug with extra steps.

Four steps, all CPU-only and portable; only step 4 touches the accelerator.

1. EMBED     question → MiniLM-L6-v2 → 384-dim, L2-normalised float32
2. RETRIEVE  FAISS IndexFlatIP → top-10 nearest pool examples (+ their cosine scores)
3. PREDICT   majority vote over those 10 neighbours' source databases  → 84.9% correct
4. ASSEMBLE  header + 10 worked examples + predicted DB's FULL schema
             + FK lines + per-DB numeric-string note + 7 rules   → ~5,755 chars
5. GENERATE  MLX-LM, greedy, max_tokens=300

Step 1–2: the retrieval design decisions

Only the question is embeddednot the query, not the schema

The retrieval job is "find past questions phrased like this one." Adding query or schema text would blur that signal with syntax irrelevant to question similarity — and more fundamentally, the incoming item is a bare NL question, so indexing question+query would embed a document no query can ever look like. Query and document must live in the same modality; the asymmetric alternative would need a dual encoder trained for it.

One embed(), imported by both sidestrain/serve skew

The index builder and the query-time retriever import the same function. The comment names the failure mode exactly: two slightly different embedding implementations "would silently misalign the space and make FAISS's nearest-neighbor search meaningless without ever raising an error." Different pooling, different truncation, different normalisation — any of them, and you get plausible-looking garbage neighbours.

Row-position alignmentthe index/metadata contract

FAISS returns integer row positions, not ids — IndexFlatIP has no id map (that would be IndexIDMap). The invariant "metadata list order == insertion order == FAISS row order" is the only thing that turns a search result back into a question. It holds because both derive from the same pool list in the same pass, and it is verified: len(metadata) == index.ntotal == 1213.

You can even read the invariants out of the index file's first bytes:

Step 3: database prediction by majority vote

def majority_vote_database(neighbor_dbs: list[str]) -> str:
    """neighbor_dbs is rank-ordered, nearest first (FAISS search order).
    Majority wins; a tie is broken by the nearest neighbor (index 0) since
    it's the single most-trusted signal FAISS gave us."""
    counts = Counter(neighbor_dbs)
    top_count = max(counts.values())
    tied = [db for db, c in counts.items() if c == top_count]
    if len(tied) == 1:
        return tied[0]
    return neighbor_dbs[0]   # tie-break: rank-1 neighbour

This is a k-NN classifier riding free on the exemplar retrieval — one embedding call serves both jobs, instead of standing up a second schema-retrieval index for a 23-way decision.

Why not Counter.most_common(1)?

Because most_common breaks ties by insertion order, which here happens to be FAISS rank order — so it would do the right thing by an undocumented implementation detail rather than by design. Making the tie-break explicit makes the semantics intentional. And it is not hypothetical: an even K makes an exact tie more likely than an odd one, which the code comment calls out directly. Measured accuracy: 258/304 = 84.9%.

Step 4: database-level schema, not collection-level

The best "why did you build it this way" answer in the repo

Once a database is predicted, its entire schema goes in the prompt — every collection, not a filtered top-k. The reason: "a fine-grained top-k collection retrieval can leave out a collection a $lookup join needs, even when the database prediction itself is correct."

Fine-grained retrieval optimises precision. A join query needs recall over the collection set, and a missing collection is unrecoverable — the model cannot write a $lookup against a collection it was never shown. At 161 cards over 23 databases (~7 collections each) a full database fits comfortably in context. The coarser retrieval unit is the safer one, and knowing when coarser is better is the point.

The negative result that was deliberately left unfixed

chinook_1 / store_1

An earlier note claimed store_1 is "confirmed identical underlying data" to chinook_1. Re-verified: true for 9 of 11 collections byte-for-byte, but Invoice.InvoiceDate is offset by a constant 2 years between exports and PlaylistTrack associations genuinely differ in membership.

Consequence: chinook_1's few-shot neighbours vote store_1 100% of the time, 0 exceptions — a guaranteed 9-case loss in the test set. And it is not fixable by retrieval: content-based retrieval structurally cannot distinguish two databases whose content is the same. The disambiguating signal — which export the gold answer came from — does not exist in the question text. No embedder fixes this.

It was left unmerged, deliberately: a full merge would need every one of chinook_1's ~42 gold queries rewritten into store_1's naming and verified not to touch InvoiceDate or PlaylistTrack, where the merge would silently produce a wrong-but-plausible answer. The code also draws the sharp distinction from the superficially similar college_1/2/3 case: that one is "a fine-tuning batch-composition bug with a clean, low-risk fix"; this one is "a RAG retrieval-ambiguity problem inherent to the data itself, with no equivalently clean fix available."

Retrieval scores — and what they tell you

The FAISS similarities used to be computed and dropped (_scores, idxs = index.search(...)). They are now persisted, and the reason is diagnostic:

"Rank alone is enough for Recall@k / MRR / nDCG, but not enough to separate a retrieval gap (the right exemplar was never retrieved at all) from retrieval noise (it was retrieved, but ranked below distractors that crowded it out)."

A real neighbourhood, for cs-e8: [0.542, 0.525, 0.519, 0.511, 0.498, 0.480, 0.480, 0.475, 0.460, 0.440]. The absolute cosines are modest and the decay is shallow — only 0.10 between rank 1 and rank 10. That flat neighbourhood is precisely why a 10-way vote is more robust than trusting rank 1, and it is also the empirical reason K grew from 3: the one retrieval miss at K=3 was a 2–1 split where two borderline neighbours outvoted one correct one.

The diagnostic that answers "what would you improve next?"

Database retrieval is 84.9%; end-to-end execution accuracy is 46.7%. Both scripts label the retrieval figure loudly as a diagnostic, not the headline. Read together they say something specific: retrieval is not the bottleneck — generation is. Even with the correct database and its full schema in front of it, the 1.5B model writes the wrong pipeline more than half the time. That is component-versus-end-to-end evaluation paying for itself, and it points the next unit of effort at the generator, not the retriever.

The opposite bet from RAG: instead of paying for grounding in the prompt on every request, pay for it once during training and carry it in the weights. Trained with mlx_lm.lora on Apple Silicon, adapter in fine_tuning/adapters_23db_1000iter/.

LoRA, precisely

A dense layer computes y = Wx. Full fine-tuning learns a dense update ΔW with as many parameters as W. LoRA freezes W and learns a low-rank factorisation of the update instead: two thin matrices A ∈ ℜd×r and B ∈ ℜr×k with r ≪ d,k, giving

y = Wx + scale · (B A) x        scale = α / r = 32 / 16 = 2.0

The hypothesis LoRA rests on is that the update needed to adapt a pretrained model to a narrow task has low intrinsic rank even though W does not. At inference the product BA can be merged back into W for zero added latency, or — as here — kept unfused so several adapters can share one base model.

Config detail worth quoting verbatim

The YAML takes scale, not alpha. The repo records the conversion rather than guessing it: scale = α/r = 32/16 = 2.0, "confirmed against ml-explore/mlx-lm's own docs and example config, not guessed". The α/r convention exists so that raising the rank does not silently change the magnitude of the update — it decouples capacity from step size.

Why LoRA and not full fine-tuning — the arithmetic, not the vibe

Memorythe binding constraint
Full FT of 1.54B params in bf16 needs weights (3.1 GB) + grads (3.1 GB) + AdamW's two fp32 moments (12.3 GB) ≈ 18.5 GB before a single activation, on a 24 GB unified-memory machine that is also running macOS. LoRA carries optimizer state for 10.55M parameters instead of 1.54B — a ~146× reduction. Observed peak: 15.45 GB.
Data219 → 1,091 examples
Full fine-tuning 1.5B parameters on ~1,000 examples is a catastrophic-forgetting machine. The rank constraint is the regulariser here — you cannot overwrite the model's Python or its MongoDB priors through a rank-16 bottleneck.
Experiment velocity42 MB per adapter
Three adapters coexist in the repo with zero risk of clobbering, each config pointing at its own adapter_path — called out deliberately so "the original 6-db training run is never at risk of being overwritten."
Servingunfused
mlx_lm.load(MODEL, adapter_path=...) applies the adapter at generation time. No fuse step, no GGUF conversion — those were only ever prerequisites for serving elsewhere, and scoring needs text, not a servable artifact.

The epoch-parity bug — the best story in the repo

When the fine-tuning arm was retrained from 6 databases to 23, iters: 200 was carried over unchanged, deliberately, as a controlled variable: "change only the data, keep training length identical." That intent was right and the execution was subtly, expensively wrong.

examples_seen = iters × batch_size × grad_accumulation_steps = iters × 4
epochs        = examples_seen / |train|

 6-db  @ 200 iters:   800 / 219  = 3.653 epochs
23-db  @ 200 iters:   800 / 1091 = 0.733 epochs   ← under 3/4 of ONE pass
23-db  @ 1000 iters: 4000 / 1091 = 3.666 epochs   ← parity restored

iters counts optimizer steps, not passes over the data. Holding steps fixed while multiplying the corpus 5× silently divides epoch coverage by 5×. So the "controlled" experiment confounded exactly the variable it was built to isolate. Its 24.0% was worse than the 6-db adapter's 36.25% in-scope score, and the naive reading — "more databases hurt" — was simply false. Solving iters × 4 / 1091 ≈ 3.65 gives iters ≈ 996, rounded to 1000. Every other hyperparameter held identical.

Payoff

73/304 (24.0%) → 103/304 (33.9%) — +30 cases, +9.9 points, from changing exactly one number. The generalisable lesson: when the dataset size changes, "same number of steps" and "same amount of training" are different claims. Decide which invariant your control actually needs — epochs, tokens, or steps — and compute it. Don't assume the config key means it.

The collision-aware batching bug

Putting all 23 schemas into every training example measured 22,955 characters (~5,700–6,500 tokens) — ~6× the original 6-db prompt, forcing max_seq_length: 8192, batch_size=1, num_layers=8. So the databases were partitioned into 6 fixed batches of ≤4, and each training example carries only its own database's batch. Largest batch: 9,797 chars (~2,800 tokens) — back in the original size class, so the already-proven memory config survived.

The first version of that partitioning sorted alphabetically and chunked. That is where it broke:

Why this is a genuinely interesting bug

Alphabetical sorting is positively correlated with semantic similarity in this dataset, because near-duplicate databases are named by suffix (college_1/2/3, flight_2/4). Chunking a sorted list therefore maximises intra-batch confusability rather than randomising it — the sort order is an adversary, not a neutral choice. The smoking gun is college_3: 0/7 correct with 0 exceptions. Zero exceptions is the tell. The queries were syntactically perfect; they just ran against a sibling's collection names. That signature says prompt-construction bug, not capability failure.

The algorithm

def _collision_group_ids(db) -> set:
    return {i for i, group in enumerate(COLLISION_GROUPS) if db in group}

def build_database_batches(databases, batch_size) -> list:
    for db in sorted(databases):              # 1. sort => determinism
        my_groups = _collision_group_ids(db)  # 2. which groups am I in?
        placed = False
        for batch in batches:                 # 3. greedy first-fit
            if len(batch) >= batch_size:                                   continue
            if any(_collision_group_ids(e) & my_groups for e in batch):    continue
            batch.append(db); placed = True; break
        if not placed:
            batches.append([db])              # 4. else open a new batch

It is graph colouring with bounded colour-class size — vertices are databases, edges are "same collision group", colours are batches, capacity 4 — solved with cheap first-fit rather than an exact solver. The failure mode of that choice is documented and benign: if COLLISION_GROUPS grows too dense, it silently opens extra batches (smaller prompts, still correct) rather than stranding a database or raising. Note the groups deliberately overlap: store_1 is in two, so it must be kept away from both chinook_1 and sakila_1.

7Normalisation — rewriting the model's dialect

Qwen was trained mostly on MongoDB-shell / JavaScript documentation, not PyMongo's Python API, and it writes accordingly. The safety guard correctly rejects both habits — null is not a Python name, .countDocuments is not a PyMongo method. The damage was counted, not estimated:

#   - bare JSON `null`/`true`/`false` where Python needs `None`/`True`/`False`
#     -- confirmed via 5 RAG-arm + 10 baseline Qwen "REJECTED by safety check
#     (unexpected name: null)" errors, 0 on Claude.
#   - camelCase Mongo-shell method names (`countDocuments`, `findOne`)
#     -- confirmed via 2 RAG-arm "method not allowed: countDocuments" errors.
Why AST and not regex — the single best soundbite in the repo

"null as a bare identifier is an ast.Name node, while the literal string "null" in quotes (a real field value some of this data actually has) is an ast.Constant node — so this only ever touches the unquoted token, never a quoted string that happens to spell the same word."

This is not hypothetical. car_1.cars_data stores missing horsepower as the string "null", and the RAG prompt explicitly tells the model to write {"MPG": {"$ne": "null"}}. A s.replace("null", "None") regex would corrupt the very guard the prompt asks for. The AST distinction makes the rewrite provably value-preserving, and there is a test pinning it.

Exactly four rewrites, no more

Renaming alone is necessary but not sufficient. The Mongo shell's countDocuments() defaults to counting everything; PyMongo's count_documents() requires an explicit positional filter. Discovered by a real post-rename crash — "count_documents() missing 1 required positional argument: 'filter'", case cs-e2. And find_one is deliberately excluded, because its filter genuinely is optional in PyMongo (defaults to None), so a zero-arg .find_one() is already valid. The asymmetry is documented rather than assumed.

Because the output is ast.unparse(node), normalisation is also a canonicalisation: quote style, whitespace and formatting are all regularised. That is what makes it usable as the equality key for self-consistency voting — two byte-different generations of the same query must count as agreement, or the agreement number is measuring formatting.

Failure mode, and the ethics of this step

except SyntaxError:

Deliberate: "execute_queries.py will correctly report this as a parse failure — better than silently mangling it into something that merely looks plausible."

Name the risk before an interviewer does

Normalisation is the most ethically dangerous step in an evaluation harness — you are editing the artifact you are grading. Four defences: (1) the rewrite set is minimal and enumerable, four rules; (2) it operates at AST level so it provably cannot touch data values; (3) every rewrite is appended to fixer.notes and printed per case, because "traceability matters here since this is a silent-by-default rewrite of the model's actual output"; (4) it is applied identically to gold and to every arm, so it cannot favour one.

Layer 2 — FORBIDDEN_OPERATORS, fail-closed, at any depth

This layer exists because the first test suite found a hole:

# Operators that execute server-side JavaScript or otherwise escape the
# read-only contract, wherever they appear. _check_pipeline_stages() below
# only inspects the top-level stage keys of an aggregate() pipeline, so a
# $where nested inside a find() FILTER -- db.x.find({"$where": "..."}) --
# went straight through it: not an aggregate() call, and just a literal dict
# as far as the outer AST allowlist is concerned. Found by tests (2026-09-05).
FORBIDDEN_OPERATORS = {"$where", "$function", "$accumulator", "$merge", "$out"}

Two families: server-side JavaScript execution ($where, $function, $accumulator — arbitrary JS in the mongod process) and writes ($out replaces a collection wholesale, $merge upserts).

The first version read only literal string keys inside literal ast.Dict nodes and skipped everything else. That is a hole, not a limitation, because Python evaluates dict keys at runtime:

db.c.aggregate([{"$o" + "ut": "pwned"}])       # BinOp key
db.c.aggregate([{f"$merge": {...}}])           # JoinedStr key
db.c.aggregate([dict([("$out", "pwned")])])    # no ast.Dict at all
db.c.find({"$wh" + "ere": "function(){...}"})  # same trick, find() filter

All four were verified to pass the old check and hand a real $out/$merge/$where to the driver.

The design principle, stated in the code

"Rather than trying to constant-fold arbitrary expressions — an endless game against str.join, .replace, %-formatting, chr() and so on — this refuses anything it cannot statically prove is a safe literal."

Three fail-closed rules: a dict key that is not a literal string Constant → reject; ** unpacking (key is None) → reject; a dict(...) constructor call → reject. This is the difference between a denylist and a sound checker: you stop enumerating what is bad and start requiring proof of what is good.

And the cost was measured before the rule shipped

"Verified free: across all 20,014 query strings in this repo's result and reference files, zero use a non-literal dict key and zero call dict(), so this rejects nothing that has ever legitimately run." A security control whose false-positive rate is measured rather than assumed is the difference between a guard you can ship and one people disable.

Layer 3 — the pipeline-stage allowlist

Where layer 2 is a denylist of five, layer 3 is an allowlist: any top-level aggregation stage key beginning with $ that is not in SAFE_PIPELINE_STAGES is rejected. That catches read-only-but-disclosing stages nobody would have thought to forbid: $indexStats, $collStats, $currentOp, $planCacheStats, $listSessions.

A regression in the opposite direction — and a great story

Re-running check_query_is_safe() over every stored query surfaced 7 gold queries stored with status: PASS that the tightened guard would now reject — $unionWith (the only way to express SQL's UNION in an aggregation pipeline) and $setWindowFields (window functions). Both are read-only. Tightening the guard had broken reproducibility of the ground truth itself: execute_gold.py could no longer regenerate 7 of its own gold results. Both operators were allowlisted; all 2,350 stored queries then pass.

Note how it was found: not by luck, and not by a user report — by replaying the new guard over the entire corpus of historical artifacts. That is a reusable verification technique.

Say the boundary out loud, unprompted. 9What counts as correct

The comparison, in full

def results_match(a, b) -> bool:
    if isinstance(a, list) and isinstance(b, list):
        # --- Tier 1: exact, order-insensitive, key-name-sensitive ---
        try:
            if sorted(map(_canonical, a)) == sorted(map(_canonical, b)):
                return True
        except TypeError:
            if a == b:
                return True

        # --- Tier 2: key-name-TOLERANT fallback ---
        if (a and b and len(a) == len(b)
                and all(isinstance(x, dict) for x in a)
                and all(isinstance(x, dict) for x in b)):
            a_vals = sorted(_values_canonical(_strip_null_id(d)) for d in a)
            b_vals = sorted(_values_canonical(_strip_null_id(d)) for d in b)
            if a_vals == b_vals:
                print("[results_match] KEY-TOLERANT match: values identical, key names differ")
                return True
        return False
    return a == b

Three helpers carry the semantics. _canonical recursively turns dicts into key-sorted tuples (so key order cannot matter — Atlas puts _id first, mongomock does not) but keeps lists as ordered tuples (so a nested array's order is significant). _strip_null_id drops _id only when its value is None — a $group: {_id: null} artifact, not data — while a non-null _id carries real information and must participate. _values_canonical discards keys entirely and returns sorted values.

The bug — read it in the package source 
code_bleu_score = (alpha * ngram + beta * weighted_ngram
                   + gamma * syntax + theta * (dataflow_match_score or 1))

In Python, 0.0 or 1 evaluates to 1. So when data-flow degenerates to zero — as it does for every arm here — the composite silently substitutes a perfect data-flow score instead of penalising the missing metric. Every arm gets a free +0.25.

Confirm it from the CSV: baseline 0.25 × (0.0003 + 0.0003 + 0.6805 + 1) = 0.4203 ✓, and the honest 3-component mean (0.0003 + 0.0003 + 0.6805)/3 = 0.2270 ✓.

There is a second, independent reason to drop it: the metric does not apply to this task. Data-flow needs variable define-use chains; db.singer.find({}, {"_id": 0}) has no variables and no statements. Note the two reasons pull in opposite directions — the or 1 bug inflates, a genuinely-zero component would deflate — but converge on the same action: exclude it, report the unweighted mean of components 1–3, and say so.

The finding this metric exists to produce

RAG 0.2783 vs fine-tuned 0.2759 — 0.0024 apart — while separating by 12.8 points on execution accuracy. Look at the components to see why: n-gram match is ~0.01 for every arm (near-zero lexical overlap; token sequences differ almost completely), so the score is carried almost entirely by syntax match. CodeBLEU here is measuring "did you produce a well-shaped PyMongo expression," which every arm mostly does — not "did you produce the right one." And fine-tuning scores higher on n-gram match than RAG (0.0155 vs 0.0098): it has learned to imitate the reference's tokens more closely while computing the right answer less often. That is the mechanism of the whole result, visible in a secondary metric.

BERTScore

Greedy-matched token-level cosine similarity between roberta-large contextual embeddings of candidate and reference (a middle layer, ~17, because middle layers correlate better with human judgment than the last). Both sides are the normalised query strings, joined on str(id) set-intersection so a missing prediction shrinks n rather than being scored as an empty string. Per-case P/R/F1 are written to CSV, not just the mean, so the distribution stays inspectable.

rescale_with_baseline=Truecosmetic, not corrective

Raw BERTScore has a compressed range — any two grammatical strings score ~0.85, so everything real lands in [0.85, 1.0]. The rescale is (raw − b) / (1 − b) against a per-model, per-layer baseline from random sentence pairs, mapping unrelated→0 and identical→1. Three things to state: it is affine and monotone, so it cannot change a ranking; rescaled scores are not comparable to raw numbers from another paper; and values can go slightly negative for worse-than-random pairs, which is not a bug.

lang="en" on source coderaise this yourself

roberta-large is a natural-language English model, not a code model. CodeBERT or GraphCodeBERT would be the code-native choice. The project inherited this from its earliest notebook and kept it for internal comparability across its own numbers — which is the right call for consistency and weakens cross-paper comparability. Say it before you are asked.

—The serving-stack confound

Lead with this one. It is the finding that involves publicly reversing your own published conclusion, and it demonstrates the thing interviewers actually want to see: that you know the difference between a result and an artefact.

What happened

For most of this project's life the three arms did not share a runtime. Baseline and RAG generated in Colab, HuggingFace transformers, fp16, shared GPU. Fine-tuning generated locally on MLX-LM, bf16, Apple Silicon — because that was the only place LoRA training could happen on the available hardware. The reported conclusion was "LoRA fine-tuning beats RAG at every K tested."

The problem, stated plainly

You cannot attribute a delta between two arms to the technique when the arms did not run on the same stack. Two arms on runtime A, one arm on runtime B, and a difference measured between them — the difference has two candidate causes and no way to separate them.

The measurement that settled it

RAG was re-run on MLX-LM against the identical 61 questions, identical gold, identical scoring code. Only the serving stack changed.

24.6% → 50.8%. More than double, on nothing but a runtime change. That single measurement reversed the project's headline conclusion.

The supporting evidence — and it is the good part

It would be easy to stop at "we changed the stack and the number moved." The project went further and established why the old number was unreliable, with a control:

The control experiment

fp16 GPU inference without deterministic-algorithm flags is not bit-identical across separate Colab sessions, even under greedy decoding. Verified directly by making a prompt-content change and its full revert back-to-back within one session and getting byte-for-byte identical output. Since the code returned to its exact prior state and the output matched, an earlier apparent accuracy swing attributed to that change could only have been driven by a session boundary, not by the code.

Contrast with the new stack: two independent full 304-case MLX runs came out identical down to the per-token logprobs. Determinism was never the goal in itself — it is the property that makes an A/B test mean anything.

How to tell this story

Three beats, in this order. (1) I found a confound in my own published result. Two arms on one runtime, one on another. (2) I removed it rather than caveated it — rewrote baseline and RAG generation onto MLX-LM so all three arms share one stack, one dtype, one tokenizer. (3) The conclusion reversed, and I published the reversal, kept the old scripts in-repo labelled as historical, and built a figure that shows both runs side by side with the honest footnote: "Fine-tuning beat RAG originally in part because RAG was measured on a noisier stack."

—Is the gold right? SQL ↔ PyMongo cross-check

Every number in this project is measured against 1,517 hand-written PyMongo queries. That is a single point of failure and an obvious question: how do you know your ground truth is right?

The design: three-way independence

Check the hand-written PyMongo against Spider's own gold SQL, executed on Spider's original SQLite files. The independence claim is precise — "a different query language, a different engine, a different author." Agreement is therefore evidence, not circularity. Nothing touches Atlas: the Mongo side is read from the already-executed gold_results.json, only the SQL side runs, and it runs locally.

Tolerances, deliberately looser than the model scorer

"This is more permissive than the scorer used for model output, and deliberately so — the goal is to surface cases where the two queries answer DIFFERENT QUESTIONS, not cases where they label the same answer differently."

Three tolerances the model scorer does not have, each necessary because the SQLite→Mongo import preserved SQLite's types: float rounding to 6dp, numeric-string coercion (a column SQLite typed TEXT is a string in Mongo but a number after SQL arithmetic), and whitespace stripping. Rows are compared as multisets, so order is ignored but duplicate counts are preserved — which is what makes DISAGREE_CARDINALITY detectable at all.

Two structural accommodations are worth naming:

The $facet shapeone row holding an array

Several gold queries express SQL's EXCEPT/INTERSECT via $facet, so Mongo returns one document holding an array where SQL returns N separate rows. Flattened explicitly, because "this shape is common rather than exotic."

AGREE_SQL_SUBSETthe extra-computed-column case

Mongo gold commonly carries an extra computed column SQL does not project — "grades with ≥4 students" returns {_id, count} in Mongo but just grade in SQL. Same answer with more detail attached, not a disagreement. Rather than loosening the comparison globally, it searches: drop each candidate key (or pair) from every Mongo row and see whether an exact match falls out, bounded by the SQL's arity so the combinatorics stay small. Testing an exception exactly beats weakening the rule for everyone.

—Confidence & calibration

Nothing in this repo used to emit a probability anywhere, so no calibration analysis was possible from its outputs at all — no ECE, no reliability diagram, no temperature scaling. Both base-model arms now record two independent signals.

Signal 1 — mean token logprob, and the trimming problem

Capturing logprobs required switching from generate() to a stream_generate() loop. The argument that this changes nothing is by construction, not by luck:

"In the installed mlx_lm 0.31.3, generate() is literally "".join(r.text for r in stream_generate(...)) — it runs this exact loop and throws the distribution away. Same kwargs, same sampler, same decode path, so swapping to this changes what is RECORDED, never what is generated."

And confirmed empirically as well as by construction: a byte-identity regression check against the pre-change results file. Argument and verification, neither substituting for the other.

Then the real problem. Because of mlx-lm issue #973 the model keeps sampling past <|im_end|> to max_tokens, so a raw generation is a short correct query followed by a long discarded tail. Across the 304 RAG cases only 19,876 of 22,139 generated tokens (89.8%) survive clean().

Why sum(logprobs)/len(logprobs) is not just imprecise, it is invalid

"A confidence number computed over text you discarded is not a confidence number for the text you kept, and any downstream calibration metric (ECE, reliability diagram, temperature scaling) built on it would be quietly, unfixably wrong."

Note the compounding: bug #973 does not merely waste compute — it corrupts the confidence signal. And in the bad cases it is far worse than 10%: a 20-token answer followed by 280 tokens of tail means ~93% of the naive average is noise.

The fix reproduces clean()'s three edits at character level (kept_char_mask), then keeps every token contributing at least one surviving character. Two subtleties in that replay are worth knowing:

Chained replaces are not two independent passes_replace_all

clean() chains .replace("```python","").replace("```",""), and each replace re-scans the previous one's output — so a backtick run like ```python`````python collapses differently under chained replaces than under two passes over the original. _replace_all rebuilds the intermediate string from surviving indices and searches that, matching str.replace's own rule: leftmost, non-overlapping, one left-to-right sweep.

The mask verifies itselfand refuses to guess

The mask is never trusted blindly: the string is reconstructed from it and compared to clean()'s actual output. If they disagree, it falls back to a coarse but always-safe trim (everything up to the first stop marker) and records which rule fired in logprob_trim_method, so a consumer can filter or audit rather than unknowingly averaging two different rules together. Across all 304 RAG cases the method used was char_mask — the fallback never fired, which is itself a verification.

Both aggregates persisted, and None not 0.0a detail that matters

mean_logprob is length-normalised and is what calibration works from; sum_logprob is the true sequence log-likelihood and penalises length. They rank candidates differently. And when zero tokens survive, both are None — because 0.0 would read as logprob 0, i.e. probability 1, i.e. maximal confidence, exactly backwards. That None then propagates correctly into the -inf tie-break guards in the self-consistency vote.

Why the vote key has to be semantic

"Two byte-different generations of the same query must count as agreement, or the agreement number is measuring formatting." Voting on raw strings would fracture a genuine 5/5 agreement into 5/5 disagreement over quote style. normalize() collapses list(db.x.find(...)) ≡ db.x.find(...), single ≡ double quotes, any whitespace, and countDocuments ≡ count_documents into one vote.

Note the two signals are combined but never conflated: the vote is semantic (AST), the tie-break is likelihood-based (logprob). Neither alone is well-defined — and with k=5, a 2–2–1 split is common, not hypothetical, so without the explicit tie-break the answer would depend on RNG draw order.

All k generations are persisted, not just the winner, and the reason is forward-looking: "an aggregate agreement fraction cannot be re-derived into a different bucketing later, and anything computing calibration downstream needs to see the spread it is calibrating." 1,520 generations on disk. The k=5 and k=1 records are shape-compatible at the top level, so nothing downstream needed changing — the winner is the arm's answer.

What the signals are actually worth

Derived for this dossier by joining the k=5 self-consistency run to the greedy run's scored execution results on id. Caveat, stated: agreement is measured on a sampled (T=0.7) run while correctness comes from the greedy run — a proxy, not the same generation. Mean logprob separates far more weakly over the same cases: −0.026 correct vs −0.065 incorrect.

The claim this supports

Agreement beats likelihood as a confidence signal on this task — which is exactly what the code comment predicted before the measurement existed: "mean logprob is the standard confidence signal and it is usually badly calibrated — the model is just as fluent when it is wrong." Keep only the 54 unanimous cases and you get 81.5% accuracy at 18% coverage. That is a selective-prediction system, and it is the most concrete "what would you build next" answer this repository supports.

Timestamp (UTC, Z-suffixed), git_sha, git_dirty, git_branch, python version, platform, mlx_lm/mlx versions, plus every caller-supplied field: arm, model, adapter, max_tokens, temp, samples, top_k, include_fk, embedding model, FAISS index type and ntotal, database retrieval accuracy, schema coverage — and results_sha256 + results_bytes.

The answer to "isn't a test asserting wrong behaviour just wrong?"

No. An untested blind spot is invisible; a characterization test is a documented, dated, cross-referenced decision with a named cost. AInterview questions — task & framing

Nine banks, ~95 questions. Click a question to reveal a defensible answer. Use it as a self-quiz: answer out loud first, then open.

Describe this project in ninety seconds.

A 1.5B open model — Qwen2.5-Coder-1.5B-Instruct, runs on a laptop — asked to turn English questions into working PyMongo queries against 23 real MongoDB databases it has never seen. Zero-shot it manages 4.9%. I compared the two standard ways of closing that gap under everything-else-held- constant conditions: retrieval-augmented prompting at 46.7%, and LoRA fine-tuning at 33.9%.

Every number is execution accuracy — the query is actually run against MongoDB Atlas and the returned documents compared to gold output. Nothing is scored by string similarity.

The two things I'd lead with First, retrieval wins, and the margin widens to ~15.4 points once I audit which "correct" answers are actually correct — fine-tuning's false-positive rate is 4× RAG's, which is what the mechanism predicts. Second, an earlier round of this project concluded the opposite, and that conclusion turned out to be a serving-stack artefact: baseline and RAG were on Colab fp16, fine-tuning was on MLX. Re-running RAG on the same stack moved it from 24.6% to 50.8% on identical questions.

Why MongoDB and not SQL? Text-to-SQL is the standard benchmark.

Two reasons, one practical and one that makes the task genuinely harder.

Practically, Text-to-SQL is saturated with prior work and I would be reproducing a leaderboard. Text-to-PyMongo has a real gap and a real audience — document stores are common in production and nobody has a comparable benchmark.

Substantively, MongoDB removes two things a SQL model gets for free. There is no declared schema, so field names and types have to be inferred from documents — and that inference is ambiguous, which is why my schema cards infer type from the first non-null value across all documents rather than from docs[0]. And there are no declared foreign keys, so the join graph does not exist anywhere; I had to mine it by parsing every $lookup stage's from/localField/foreignField triple out of the gold queries.

The target language is also harder: an aggregation pipeline is an ordered array of stages embedded in a Python expression, not a flat declarative sentence, so there are more ways to be structurally valid and semantically wrong.

Why execution accuracy rather than exact match or BLEU?

Because a query is correct if it returns the right rows, and many textually different queries do. Exact match punishes every legitimate alternative formulation; my own data shows a baseline query and a fine-tuned query reaching the same right answer by entirely different pipelines.

And I have the receipt, not just the argument RAG and fine-tuning score 0.2783 vs 0.2759 on CodeBLEU — a 0.0024 gap — while separating by 12.8 points on execution accuracy. Look at the components and you see why: n-gram match is ~0.01 for every arm, so the score is carried almost entirely by AST syntax match. CodeBLEU is measuring "did you produce a well-shaped PyMongo expression," which every arm mostly does — not "did you produce the right one."

Fine-tuning even scores higher on n-gram match than RAG (0.0155 vs 0.0098) while scoring 12.8 points lower on execution. It learned to imitate the reference's tokens more closely and compute the right answer less often. That is the whole finding, visible in a secondary metric.

What's the weakness of execution accuracy, then?

The mirror image: many semantically different queries return the same result. That is a false positive, and I audited it rather than hand-waving it.

Four specific classes are admitted by result comparison. Empty matches empty — a wrong query that also returns nothing passes. Scalar matches scalar — a count is a one-dimensional projection, so coincidence is cheap on small databases. Order is never compared, so a reversed or absent sort is invisible. Low cardinality — "top 3" over a collection with exactly 3 distinct values returns all of them regardless of ranking.

Measured: 14 confirmed false positives across 114 flagged candidates, and importantly 10 false negatives too. Corrected, RAG goes 141→138 and fine-tuning 103→94 — the gap widens.

Why a 1.5B model? Wouldn't a frontier model just solve this?

It largely does — my Stage 1 comparison had Claude at 55.4% versus Qwen at 4.3% on the original corpus. That is exactly why it is the wrong question to spend a capstone on.

The interesting question is what closes that gap without a frontier model, because the deployment constraints that make a small local model attractive are real: data residency (the schema and the questions may not leave the building), per-query cost at volume, latency, and offline operation. This project is a controlled measurement of how much of that gap two standard adaptation techniques recover, on hardware you can buy once.

And it makes the negative results informative On a frontier model, retrieval-vs-fine-tuning differences would be swamped by raw capability. At 1.5B the mechanisms are visible — you can see fine-tuning learning query shape while getting predicates wrong, because it does not have the headroom to hide it.

Why is the baseline so bad — 4.9% seems implausibly low.

Look at the failure mix rather than the number. 172 of 304 baseline queries ran cleanly and returned nothing. Only 49 hard-failed. The model is not producing broken Python — it produces well-formed PyMongo against collection and field names it invented, or the right names in the wrong casing.

So it is a schema-linking failure, not a code-generation failure. And the condition is genuinely hard: one fixed 23,825-character prompt containing all 23 databases' schemas, no examples, and the model must first work out which database the question is even about. That is a needle in 161 collections with no pointer.

Why this matters methodologically An accuracy number tells you the model is bad. The four-bucket outcome mix tells you why — and that diagnosis is exactly what motivates both adapted arms. It is the single strongest argument for reporting a funnel instead of one number.

Where did the data come from, and how much of it is yours?

23 databases from Spider, the cross-domain Text-to-SQL benchmark, converted to MongoDB collections — one table to one collection, one row to one flat document, no denormalisation and no type coercion. The questions are Spider's.

What is mine is the gold: 1,517 hand-written, hand-verified PyMongo queries, grown across three expansion rounds from an original 12. That is the expensive part and the single point of failure, which is why I cross-checked it against Spider's own gold SQL executed on Spider's original SQLite files — different language, different engine, different author. 1,264 of 1,409 agree, 89.7%, zero SQL errors.

Why did you preserve the relational structure instead of denormalising into documents?

Because denormalising would have deleted the hard part of the task. If I embed the related documents, a question that requires a join becomes a single-collection find() — and I would be measuring something much easier while calling it the same benchmark.

Keeping tables as separate collections with the same scalar key columns means a SQL JOIN must become an explicit $lookup that the model writes. FK knowledge is re-introduced later only as prompt metadata, never as a data transformation.

The cost, honestly This is not idiomatic MongoDB modelling — a real Mongo schema for this data would embed. So my benchmark measures translation into a relational-shaped document store, which is a real deployment pattern (a lift-and-shift) but not the only one.

Your gold data has type problems — numbers stored as strings. Isn't that dirty data?

It is inherited, not introduced, and that distinction matters. SQLite is dynamically typed per value: a column declared INTEGER can hold the text '150' or the text 'null'. The row-by-row conversion preserves that faithfully, so cars_data.Horsepower is a string in Mongo because it was a string in Spider.

I chose to surface it rather than silently coerce it. Coercing would have been a hidden transformation of the benchmark, and it would have removed a genuinely realistic difficulty — real production data has exactly this problem.

And it earned its keep as a finding That one data property drives a scoped prompt note, a schema-card annotation, a bad_type_cast bucket in the bug taxonomy, and 50 of the 145 gold cross-check disagreements. It also produces the nastiest silent failure in the corpus: "11" > "9" is False as strings. A join with a type mismatch returns empty and you notice; a numeric filter on strings returns the wrong rows and you do not.

BInterview questions — your own numbers

Give me the three headline numbers and their sample size.

On a 304-case held-out test set, all three arms on one serving stack: baseline 15/304 = 4.9%, RAG at K=10, 142/304 = 46.7%, LoRA fine-tuned, 103/304 = 33.9%.

The worst-case standard error on a proportion at n=304 is ±2.9 points (that is √(0.25/304), the widest a binomial gets, at p=0.5). So the 12.8-point RAG-over-fine-tuning gap is roughly 4 standard errors — comfortably real. The 0.33-point FK A/B difference is not.

A detail worth volunteering That SE is computed in the scoring script from whatever n the run actually has, with a comment saying it is deliberately not carried over from an earlier, smaller split. A stale error bar is as misleading as a stale number.

Is a 12.8-point gap on 304 cases actually significant?

Yes, but let me be precise about which test applies. These are paired observations — the same 304 questions answered by both arms — so the right test is McNemar's on the discordant pairs, not a two-proportion z-test that treats them as independent samples.

I have the discordant counts: RAG-correct-and-FT-wrong is 77, FT-correct-and-RAG-wrong is 39. Under the null those 116 discordant pairs split 50/50; observing 77/39 is about 3.5 standard deviations out (√116/2 ≈ 5.4, and 77−58 = 19). So it is significant at any conventional threshold, and the paired test is more powerful than the unpaired one because the 64 both-correct and 124 both-wrong cases carry no information about the difference.

The honest caveat I did not run McNemar in the repo — the repo reports a worst-case SE. I can compute it from committed artifacts, and I would state that distinction rather than claim a test I did not run.

Walk me through the outcome mix for each arm and what it tells you.

Four buckets, priority-ordered: correct, hard-fail, ran-but-empty, wrong-but-non-empty.

  • Baseline: 15 / 68 / 172 / 49. Dominated by empty. Invented names.
  • RAG: 141 / 86 / 63 / 14. Hard failures collapse from 49 to 14 — the worked examples teach valid syntax — and empties more than halve, because the schema is right in front of it.
  • Fine-tuned: 103 / 105 / 80 / 16. Note the shape difference: fine-tuning's largest non-correct bucket is wrong-but-non-empty, 105 cases.

That shape difference is the finding RAG's residual failures skew toward returning nothing; fine-tuning's skew toward returning something wrong. That is the same mechanism as the false-positive gap: LoRA learned the shape of a valid pipeline, so it confidently produces plausible output with the wrong predicate inside. A query that returns nothing announces its failure. A query that returns the wrong rows does not.

Break the results down by difficulty.

Easy 75 cases: baseline 9.3%, RAG 60.0%, FT 54.7%. Medium 111: 4.5% / 40.5% / 28.8%. Hard 39: 0.0% / 28.2% / 17.9%. Plus 79 unlabelled cases at 3.8% / 50.6% / 29.1%.

The unlabelled bucket 79 of 304 cases have no complexity label — a genuine data-quality gap from the newest expansion round. I show it as its own bar rather than dropping it or force-fitting it, because dropping it would silently remove 26% of the test set from a complexity breakdown. Its numbers sit between easy and medium, which is consistent with it being a mixed bag rather than a systematically different population.

Do the two arms fail on the same cases?

No, and this is the most actionable result I have. Out of 304: both correct on 64, RAG-only 77, fine-tuned-only 39, neither 124. Union 180/304 = 59.2%.

So an oracle that picked the right arm per case would score 59.2% — 12.5 points above RAG alone. The arms are complementary, not redundant.

Which is exactly why the confidence work matters A real router needs a signal to choose with. I have one: self-consistency at k=5 gives 81.5% accuracy when all five samples agree versus 22.4% below 0.6 agreement. That is the concrete next build, and the 59.2% union is its headroom.

What is your database-retrieval accuracy and why does it matter?

258/304 = 84.9% at K=10 — that is how often the majority vote over the ten retrieved neighbours picks the correct database out of 23. It was 96.7% on the original 6-database slice, which is the expected drop for a 23-way problem.

It matters because it separates component from end-to-end performance. Retrieval 84.9%, end-to-end 46.7%. Read together those say something specific: retrieval is not the bottleneck — generation is. Even handed the correct database and its full schema, the 1.5B model writes the wrong pipeline more than half the time. That points the next unit of effort at the generator, not the retriever.

Both scripts label it loudly as a diagnostic and not the headline, precisely so nobody quotes 84.9% as an accuracy figure.

What is the ceiling on this benchmark? Could an arm score 100%?

No, and I can quantify part of why. The SQL cross-check found 37 TIE_OR_RANK cases where the question is genuinely under-determined. spider-network_1-7 asks which grade has the most high schoolers when grades 9, 10, 11 and 12 all have exactly four. SQL's arbitrary pick is 12; the gold PyMongo adds an _id tiebreak and picks 9. A model answering "12" is scored wrong for an equally correct answer.

That is a property of the questions, not of either query language, not of the gold, and not of the model. It caps how high any arm's measurable accuracy can go.

There are two more ceilings: 9 chinook_1 test cases are structurally unretrievable because chinook_1 and store_1 are near-identical data under different names, so neighbours vote store_1 100% of the time; and 4 gold queries return empty. Knowing that a slice of your own test set is unanswerable is a stronger position than reporting 46.7% as if the other 53.3% were all model error.

CInterview questions — RAG deep-dive

Walk me through your retrieval pipeline end to end.

Five steps. One: embed the incoming question with all-MiniLM-L6-v2 — mean-pooled over tokens with the attention mask, L2-normalised, 384-dim float32. Two: search a FAISS IndexFlatIP holding 1,213 pool questions, get the top 10 by cosine, and keep the scores. Three: majority-vote those 10 neighbours' source databases to predict which database the question is about — 84.9% correct. Four: assemble a prompt: shared header, the 10 worked examples in rank order, the predicted database's entire schema with FK lines, a database-scoped type warning, and seven rules. Five: generate with MLX-LM, greedy, max_tokens=300.

Steps 1–4 are CPU-only and portable; only step 5 touches the accelerator. That separation is deliberate — it means the prompt build does not need rebuilding when the serving stack changes.

Why IndexFlatIP and not IVF or HNSW?

Because at 1,213 vectors an approximate index is strictly worse on both axes. You trade exact recall for a latency saving that is unmeasurable: 1,213 × 384 float32 is 1.86 MB, and a full scan is sub-millisecond.

IVF has a harder problem: it requires a train() step, and FAISS wants roughly 39×nlist training points, so a 1.2k-vector IVF index would be under-trained by construction. HNSW is pure memory and build overhead here.

The general point ANN indexes exist to avoid scanning millions of vectors. Reaching for one at this scale is over-engineering by two orders of magnitude. I'd rather be able to explain why exact search is right than have used the fancier thing.

Why does the index only contain questions, not questions plus queries?

Because the query key and the document key must live in the same modality. The incoming item is a bare natural-language question. If I index question+query, I have embedded a document that no query can ever look like — a representation mismatch that silently degrades every neighbour without raising anything.

The retrieval job is specifically "find past questions phrased like this one." Adding query or schema text blurs that semantic signal with syntax that has nothing to do with question similarity.

The alternative — asymmetric or query-to-document retrieval, where the two sides are legitimately different — needs a dual encoder trained for it, which is out of scope for a bi-encoder used off-the-shelf.

How do you know your query vectors land in the same space as your index vectors?

Because both sides import the same embed() function from one module. That is the whole mechanism, and the comment names the failure mode exactly: two slightly different embedding implementations "would silently misalign the space and make FAISS's nearest-neighbor search meaningless without ever raising an error."

Concretely, the things that could diverge are pooling strategy, truncation length, whether you normalise, and dtype. Any one of them differing gives you plausible-looking garbage neighbours with no exception. It is the retrieval version of train/serve skew.

There is a second invariant beside it: FAISS returns integer row positions, not ids — IndexFlatIP has no id map. So "metadata list order == insertion order == FAISS row order" is the only thing that turns a search result back into a question. It holds because both come from the same list in the same pass, and it is checked: len(metadata) == index.ntotal == 1213.

Why majority vote for the database rather than just taking the nearest neighbour?

Because the neighbourhood is flat. A real top-10 for one case: [0.542, 0.525, 0.519, 0.511, 0.498, 0.480, 0.480, 0.475, 0.460, 0.440] — only 0.10 between rank 1 and rank 10. When the similarity gap is that small, rank 1 is not meaningfully more trustworthy than rank 3, so a vote is more robust than a single draw.

That is not theoretical: the reason K grew from 3 to 5 was a specific retrieval miss where a 2–1 split let two borderline neighbours outvote one correct one. A wider vote is less exposed to a couple of noisy nearest hits.

One detail I'd point at I don't use Counter.most_common(1), because it breaks ties by insertion order — which here happens to be FAISS rank order, so it would do the right thing by an undocumented implementation detail rather than by design. The explicit tie-break to the rank-1 neighbour makes the semantics intentional. And an even K makes exact ties more likely, which is precisely why that branch exists.

Why do you inject the whole database schema rather than retrieving the relevant collections?

This is my favourite design decision in the project. Fine-grained collection retrieval optimises precision. But a join query needs recall over the collection set, and a missing collection is unrecoverable — the model cannot write a $lookup against a collection it was never shown. There is no graceful degradation.

Meanwhile the cost of being coarse is bounded: 161 collections over 23 databases is ~7 per database, so a full database schema fits comfortably in context. I am paying a few hundred tokens to eliminate an entire failure class.

The transferable principle Choose your retrieval granularity by asking what an omission costs, not by asking what is most precise. Here a false negative at the collection level is fatal and a false positive is nearly free, so the coarser unit is the safer one.

Why K=10? Did you tune it?

I swept K = 3, 5, 10 on the earlier 61-case matched slice and accuracy rose monotonically: 21.3% → 22.9% → 24.6%. K=10 is the top of the tested range, and I did not go higher.

Two honest caveats First, that sweep was on the old Colab stack — the same stack I later showed was noisy across sessions — so the monotonicity is directional, not precise. I have not re-run the sweep on MLX at n=304, and I should. Second, at n=61 the worst-case SE is ±6.4 points, so those three points are all within noise of each other individually; it is the monotone ordering that carries the signal, weakly.

Making K a CLI flag rather than a constant was itself a fix: it had previously been changed by hand across three different dataset sizes, which confounded "more examples" with "bigger pool, bigger test set." Comparing K on a fixed split required it to be a parameter.

You put the most similar example first. Does order matter?

It plausibly does and I did not test it — that is a real gap. Neighbours appear in FAISS rank order, so Example 1 is the nearest.

The argument for reversing it is mid-context attenuation: models attend more strongly to the beginning and end of a long context, so the most relevant exemplar arguably belongs last, immediately before the question. With a ~5,755-character prompt this is a live concern, not a theoretical one.

It is a cheap ablation — one flag in the prompt renderer, one regeneration, one scoring run — and it is on the list right behind re-running the K sweep on the current stack. I would rather name it as untested than claim rank order was a considered decision.

Your FK annotation experiment found nothing. Why is that worth talking about?

Because of how it was run, not what it found. Four things make it a real experiment:

  • One lever. render_schema_block(..., include_fk=) — the same script run twice, rather than diffing two prompt styles that also differ in unrelated ways.
  • A pre-flight assertion before spending compute: assert nofk_count == 0, 'nofk variant leaked an FK line'.
  • A free negative control. FK edges only exist for 6 of 23 databases, so the other 17 render identically in both variants — their scores are a built-in consistency check that nothing outside the target databases moved.
  • Power stated in advance: at n=304, SE ≈ 2.9 points; 1–4 cases is inside noise, 9+ cases would be a signal.

The strongest part I pre-registered the interpretation: before the number came in, the guide said FK annotations are low-cost metadata that improve prompt interpretability, so keeping them is reasonable even on a neutral result. That converts a null result from a disappointment into a finding — FK lines do not help on top of what schema plus ten worked examples already provide, which tells you where the remaining headroom is not.

Your prompt has seven hand-written rules. Isn't that just prompt hacking?

Every rule traces to a counted failure, and I can name the count for most of them. Rules 1–4 are output-format constraints inherited verbatim from the baseline prompt. Rule 2's db['model_list.json'] clause exists because one collection's name literally contains a dot, which dot-attribute access cannot express.

Rule 5 is scorer-aware: results_match() compares full documents, so a stray ObjectId fails the match even when every other field is right. Note it tells the model why, not just what. Rule 6 is the instruction that actually activates the retrieved exemplars — without it they are decoration. Rule 7 is a distilled MongoDB semantics trap: $size as a query operator takes only a literal integer, and two escape hatches are given.

Where I'd push back on myself Rule 5 is arguably teaching to the test — I am telling the model how to satisfy my comparator. I would defend it as normalising an artefact (_id is not part of the answer to any of these questions), and I'd point out that the audit surfaces the mirror problem honestly: ONLY_ID_DIFFERS is my dominant false-negative class, so the rule does not fully work anyway.

You have databases that retrieval structurally cannot tell apart. What did you do?

Documented it and deliberately did not fix it. chinook_1 and store_1 are the same underlying data under two naming conventions — I verified 9 of 11 collections are byte-identical, with Invoice.InvoiceDate offset by a constant two years and PlaylistTrack membership genuinely differing.

Consequence: chinook_1's neighbours vote store_1 100% of the time, zero exceptions. A guaranteed 9-case loss.

Why it is unfixable by retrieval Content-based retrieval cannot distinguish two databases whose content is the same. The disambiguating signal — which export the gold came from — does not exist in the question text. No embedder fixes this; a bigger model does not fix this.

And I'd draw the contrast with the superficially similar college_1/2/3 problem, which I did fix: that one is a fine-tuning batch-composition bug with a clean, low-risk fix. This one is a data-identity problem where a merge would need every one of ~42 gold queries rewritten and verified not to touch the two collections where the merge produces wrong-but-plausible answers. Knowing which bugs to leave alone is a skill.

Why did you store the FAISS similarity scores? Ranks are enough for Recall@k.

Ranks are enough for Recall@k, MRR and nDCG. They are not enough to tell a retrieval gap from retrieval noise — whether the right exemplar was never retrieved at all, or was retrieved and outranked by distractors. Those two have completely different fixes: one is an embedding or corpus problem, the other is a reranking problem.

The scores were being computed and thrown away — _scores, idxs = index.search(...). Persisting them was verified purely additive: rebuilding changed 0 of 304 system prompts and 0 of 304 retrieved-id lists, and added exactly one key.

They also turned out to be directly informative: the modest absolute cosines (0.44–0.54) and shallow decay are the empirical justification for voting over ten neighbours instead of trusting one.

RAG adds latency and prompt size at inference. Is that a fair comparison to fine-tuning?

It is a fair accuracy comparison and an incomplete cost comparison, and I would say so.

The accuracy comparison is controlled: same model, same serving stack, same decoding, same scoring code, same information source — both arms consume the same 1,213-case pool, RAG at query time and LoRA at training time.

The cost picture is genuinely asymmetric. RAG pays ~5,755 characters of prompt per request plus an embedding call and a FAISS search, forever. LoRA pays ~1 hour of training once and then serves with an unfused 42 MB adapter at essentially base-model cost. At high query volume that flips the economics.

What I did not measure Tokens per query, TTFT, and cost per thousand queries. Prompt length drives prefill cost specifically, which is compute-bound and scales with prompt tokens — so RAG's ~5.7k-character prompts are a real serving cost that my accuracy table does not show. That is exactly the axis my sibling serving-benchmark project measures.

DInterview questions — fine-tuning deep-dive

Explain LoRA as if I don't know it.

A dense layer computes y = Wx. Full fine-tuning learns a dense update ΔW with as many parameters as W. LoRA freezes W and learns a low-rank factorisation of the update instead — two thin matrices A (d×r) and B (r×k) with r much smaller than d — giving y = Wx + (α/r)·BAx.

The hypothesis it rests on is that the update needed to adapt a pretrained model to a narrow task has low intrinsic rank, even though W itself does not. At inference BA can be merged into W for zero added latency, or kept unfused so several adapters share one base model — which is what I do.

Mine: rank 16, α 32, so scale = 2.0. 16 of 28 layers, 7 modules per layer, 10,551,296 trainable parameters = 0.684% of 1.544B.

Why alpha 32 with rank 16 — what does the ratio do?

The scale α/r decouples the update's magnitude from its capacity. If you raise the rank without changing α/r, the effective step size of the update stays stable, so you can sweep rank without re-tuning the learning rate. That is the whole reason the convention exists.

A detail I'd volunteer The MLX config takes scale directly, not alpha — the installed mlx-lm 0.31.3 dropped the --lora-parameters CLI flag entirely. So the YAML records the conversion in a comment: scale = α/r = 32/16 = 2.0, "confirmed against ml-explore/mlx-lm's own docs and example config, not guessed." Writing down the conversion rather than eyeballing it is the kind of thing that saves you six months later.

Which modules did you adapt, and how do you know?

All four attention projections and all three MLP projections — q, k, v, o, gate, up, down — on the top 16 of 28 layers. That is the "attention + MLP" variant, not the original LoRA paper's q/v-only recipe.

And I know because I read it out of the safetensors header, not because the config says so: 224 tensors = 16 layers × 7 modules × 2 matrices, adapted layer indices exactly 12–27. Summing the shapes gives 10,551,296 exactly, which matches the trainer's own first log line, Trainable parameters: 0.684% (10.551M/1543.714M), and 42,229,570 bytes on disk ≈ 10.55M × 4 bytes F32 plus header.

One thing the shapes tell you for free k_proj and v_proj have output dimension 256 while q_proj and o_proj have 1536. That is the GQA signature: 12 query heads, 2 KV heads, head_dim 128, so 2×128 = 256. You can read the attention architecture off the adapter file.

Why the top 16 layers rather than all 28, or the bottom 16?

Two reasons. Substantively, the task is output shaping layered on top of an already-strong code model — the model knows Python and knows MongoDB; what it needs to learn is a fixed output format and a set of schemas. Later layers dominate output form, so that is where the adapter buys the most.

Practically, num_layers is the documented memory lever. The config comment says explicitly that if a smoke test OOMs, batch_size=1 is the next lever and num_layers=8 the one after that.

Honest caveat I did not ablate it. 16 was chosen by reasoning plus memory headroom, not measured against 8 or 28. If pressed on what I'd test first with more compute, layer count and rank are the two obvious sweeps — and I'd expect rank to matter less, since 10.5M parameters is already far more than needed to learn an output format.

Why LoRA rather than full fine-tuning? Give me the arithmetic.

Full fine-tuning 1.544B parameters in bf16 needs weights 3.1 GB, gradients 3.1 GB, and AdamW's two fp32 moments at 12.3 GB — about 18.5 GB before a single activation, on a 24 GB unified-memory machine that is also running macOS. LoRA carries optimizer state for 10.55M parameters instead of 1.544B, roughly a 146× reduction. Observed peak: 15.45 GB.

Second reason: data. Full fine-tuning 1.5B parameters on 1,091 examples is a catastrophic-forgetting machine. The rank bottleneck is the regularisation — you cannot overwrite the model's Python priors through a rank-16 subspace per matrix.

Third: experiment velocity. 42 MB adapters mean three of them coexist in the repo, each config pointing at its own adapter_path, so no experiment can silently clobber another.

Tell me about the worst bug in your fine-tuning pipeline.

The epoch-parity bug, and what makes it good is that the intent was right.

When I retrained from 6 databases to 23, I kept iters: 200 unchanged deliberately, as a controlled variable — "change only the data, keep training length identical." That sounds like the correct experiment. But iters counts optimizer steps, not passes over the data:

 6-db @ 200:   200×4 =  800 /  219 = 3.65 epochs
23-db @ 200:   200×4 =  800 / 1091 = 0.73 epochs  ← under 3/4 of ONE pass

Holding steps fixed while multiplying the corpus 5× divided epoch coverage by 5×. So the "controlled" experiment confounded exactly the variable it was built to isolate. Its 24.0% was worse than the 6-db adapter's 36.25% in-scope score, and the naive reading — "more databases hurt" — was simply false.

Solving for parity gave iters ≈ 996, rounded to 1000. Nothing else touched. Result: 73/304 → 103/304, +9.9 points from changing one number.

The generalisable lesson When the dataset size changes, "same number of steps" and "same amount of training" are different claims. Decide which invariant your control actually needs — epochs, tokens, or steps — and compute it. Don't assume the config key means it.

Your validation loss was 0.057 at iteration 200 and 0.024 at 1000. Would you have caught that bug from the loss curve?

No, and that is the more uncomfortable half of the story. From iteration ~420 to 1000, validation loss moves 0.028 → 0.024 — essentially noise — while execution accuracy moved substantially.

Token-level validation loss is a poor proxy for execution accuracy on this task. If I had only had the loss curve, I would have early-stopped around 400 and left points on the table.

Why the proxy is weak here Cross-entropy over tokens rewards getting most of a long query textually right. Execution accuracy is binary and depends on a handful of load-bearing tokens — a field name, a comparison direction, a $toInt. You can reduce average token loss substantially while flipping zero cases from wrong to right, and vice versa.

It is the same argument as CodeBLEU-versus-execution, one level down. And it is precisely why the project's real metric is the Atlas execution eval and not the curve.

Tell me about the collision bug.

Putting all 23 schemas in every training example measured ~22,955 characters, about 6× the original prompt, forcing a much more expensive memory config. So I partitioned the databases into six fixed batches of at most four, and each training example carries only its own database's batch. That keeps the largest prompt at ~9,800 characters, back in the original size class.

The first version sorted alphabetically and chunked. That put chinook_1, college_1, college_2 and college_3 in one batch — the three colleges share a domain and differ only in naming convention (UPPERCASE, lowercase, TitleCase). The model learned to answer college_3 questions using its siblings' field names.

Measured: that batch scored 8/79 (10.1%) versus 55/225 (24.4%) for every other batch, and college_3 was 0/7 with zero exceptions.

Zero exceptions is the tell The queries were syntactically perfect. They just ran against a sibling's collection names. That signature says prompt-construction bug, not capability failure — and it is how I knew where to look.

Why did alphabetical batching fail? Isn't sorting neutral?

That is the interesting part: alphabetical order is positively correlated with semantic similarity in this dataset, because near-duplicate databases are named by suffix — college_1/2/3, flight_2/4. So chunking a sorted list maximises intra-batch confusability rather than randomising it. The sort order is an adversary, not a neutral choice.

The fix is a collision-aware greedy first-fit: an explicit COLLISION_GROUPS list, then place each database into the first open batch that has capacity and shares no collision group with any existing member; otherwise open a new batch. It is graph colouring with bounded colour-class size — vertices are databases, edges are "same collision group", capacity 4 — solved with cheap first-fit rather than an exact solver.

Two details I'd point out: the groups deliberately overlap (store_1 is in two, so it must be kept from both chinook_1 and sakila_1); and the degradation mode is benign — if the groups grow too dense, it silently opens more batches, meaning smaller prompts, rather than stranding a database or raising.

How do you guarantee the training prompt matches the inference prompt?

Structurally, not by convention. The generation script does not recompute the batching — it reads the literal, already-assembled system-prompt text for each batch straight out of the training run's own split_manifest.json.

The reasoning, quoted: "Two independent scripts 'computing the same deterministic batching' sounds safe until pool/test files or BATCH_SIZE drift between when one runs and when the other runs — reading the literal recorded prompt text removes that risk entirely, not just makes it unlikely."

And it is fail-closed: a missing manifest raises RuntimeError, and a test database with no batch prompt raises RuntimeError naming the databases and telling you the test file has changed since prep last ran. Never a guessed fallback.

Why this generalises Train/serve skew usually comes from two code paths believed to be equivalent. The robust fix is to make one of them data that the other reads, rather than a second implementation.

How do you know there's no data leakage?

Three assertions plus one structural defence.

Assertion 1: id overlap between pool and held-out test must be empty. Assertion 2: exact question-text overlap must be empty — strictly stronger, because it catches the same question assigned two different ids, which disjoint id sets would miss entirely. Assertion 3: the id space is actually a key (len(set(ids)) == len(cases)) — without which assertion 1 is meaningless. Results are persisted into the manifest so the split is auditable without re-running. All empty; I re-verified both independently while writing this.

The structural defence is the part I like The held-out set is copied through deliberately misshapen: a JSON array not JSONL, no messages key, and named holdout_eval_cases.json rather than test.jsonl — specifically "so nothing about this file invites mlx_lm.lora --data ... --test to touch it." The assert catches drift; the filename makes the accident impossible in the first place.

You set dropout to 0.0. Defend that.

Honestly? It is the mlx-lm default and I did not tune it — there is no comment in the repo defending it, and I would say that rather than invent a rationale.

The post-hoc defence is reasonable: the target is a deterministic, low-entropy string; the regularisation actually in play is the rank bottleneck plus early stopping by iteration count; and the loss curve shows no overfitting signature — validation stays at or below training throughout the tail and plateaus rather than turning up.

But "no overfitting appeared" is weak evidence when validation loss is a poor proxy for the real metric. If I ran this again, dropout would be in the sweep alongside rank and layer count.

Is there anything about your training setup you'd change first?

mask_prompt: false — a default the config never sets and I did not notice until auditing the adapter config. Loss is computed over the whole sequence: system prompt, question and answer.

With a 1,500–2,800-token schema prompt and a 50–150-token answer, most of the gradient signal is the model re-predicting its own fixed system prompt. That both dilutes the useful signal and flatters the loss curve — a lot of that 0.024 is the model getting very good at reciting a constant.

Masking the prompt so loss is computed on the assistant turn only is a one-line config change with a plausibly large effect, and it is the first thing I would test. Second would be steps_per_eval: at 20, validation consumed ~33% of total wall clock for a signal I have just argued is weak.

Your 6-db adapter scored 36% in-scope and 8% out-of-scope. What does that tell you?

That a narrow LoRA adapter transfers poorly to schemas it never saw — 36.25% on its own six databases, 8.48% on the other 224 cases. That gap is the entire motivation for the 23-database retrain.

It is also the strongest single argument for retrieval on this task, and I would put it exactly this way: retrieval generalises to a new database by adding a row; LoRA generalises to a new database by retraining. In any setting where schemas change — which is most settings — that difference dominates the 12.8-point accuracy gap.

One piece of engineering I'd point at The scoring script refuses to report a single pooled number for those 304 cases, because they are not one homogeneous population. The CSV row is literally named AllPooled_DO_NOT_QUOTE_ALONE. The caveat is carried in the data, not in a docstring someone might not read.

Would quantising the adapter or the base model change your conclusions?

I did not test it here, so the honest answer is that I don't know for this task — but I have adjacent evidence from a sibling project that benchmarked the same fine-tuned model across four serving stacks: 4-bit quantisation cost at most ~3 accuracy points, and not consistently downward, against a ~3× throughput gain.

My expectation for this task specifically is that quantisation would hurt the fine-tuned arm more than the RAG arm, because fine-tuning's signal lives in a small low-rank perturbation that quantisation noise can plausibly swamp, whereas RAG's grounding lives in the prompt and is unaffected by weight precision.

That is a hypothesis with a clean experiment attached, not a result, and I would label it as such.

EInterview questions — evaluation methodology

How exactly do you decide two result sets match?

Two tiers. Tier 1 canonicalises both sides — dicts become key-sorted tuples so key order cannot matter, lists stay ordered tuples so nested array order does matter — then sorts both row lists and compares. So row order is ignored, key order is ignored, key names matter, duplicates matter (it is a multiset comparison), and there is no float tolerance: exact equality.

Tier 2 is a key-name-tolerant fallback, gated on both sides being non-empty, equal length, and all dicts. It strips a null _id (a $group: {_id: null} artefact, not data — a non-null _id carries real information and must participate) and compares sorted values only. That exists because the model writes {'max': 640} where gold says {'max_charge_amount': 640}.

And tier 2 is instrumented Every tier-2 match prints a KEY-TOLERANT line, so every use of the permissive path is visible in run logs and the audit re-derives it as a flag — 37 occurrences.

Isn't the key-tolerant tier dangerous?

Yes, and it is the extension I am least comfortable with. It discards column semantics entirely, so a transposed result matches. There is a test asserting exactly that: results_match([{"wins":3,"losses":5}], [{"losses":3,"wins":5}]) is True.

Note also its gate is len(a) == len(b), which is a row-count check, not a column check — so same-arity, different-key rows match.

Why it is still there Without it, a large class of legitimately correct queries fails on an alias. The right framing is that this is a measured trade: I made the comparison more permissive, then measured the resulting error rate (14 confirmed FPs, of which the tolerant tier is one contributing mechanism), and pinned the blind spot as a test so tightening it is a visible assertion flip. What I would not defend is having added it without that measurement, which is what happened originally — the tests came later, and their whole rationale is that four extensions had each been made by reasoning rather than by pinning behaviour.

You have no float tolerance. Is that a problem?

Not currently, and I can say why precisely: gold results and predictions are produced by the same engine on the same cluster, so an $avg computed twice gives bit-identical floats. The comparison is exact and that is fine.

It would bite the moment that stops being true — if gold were regenerated on a different MongoDB build, or compared across engines. And there is an asymmetry worth naming: my SQL cross-check does round to 6 decimal places and does coerce numeric strings, because there it is comparing across two genuinely different engines. So the codebase already contains the tolerant version; the strict one is a deliberate choice for the same-engine case.

If I were hardening this for reuse I'd add an explicit tolerance with a documented epsilon rather than relying on an environmental coincidence.

Why is order-insensitivity a feature and not a bug?

Because MongoDB genuinely has no inherent document order without an explicit $sort. An order-sensitive comparison would produce false negatives on every unsorted query — the same correct query would pass or fail depending on storage order.

The price is a blind spot on questions that do ask for an order, and I pay it knowingly: it is one of my four documented false-positive classes, with a confirmed case (spider-wine_1-30 sorts on Price after a $project that removed it, so its output order is arbitrary, on a question that asks for price order).

How I mitigate rather than fix The audit flags NO_SORT_IN_PRED and SORT_SPEC_DIFFERS — and the latter is gated by a regex on the question for ordering words, so it only fires when the question actually asks for an order. That narrows a structural blind spot to a reviewable list.

How do you know your ground truth is right?

I cross-checked it against Spider's own gold SQL, executed on Spider's original SQLite files. The independence is three-way: different query language, different engine, different author. So agreement is evidence rather than circularity.

All 1,396 Spider-derived cases resolve on a (db_id, normalised question) join. 1,409 execute on both sides. 1,264 agree — 89.7% — with zero SQL errors, and 87.2% on the test slice specifically.

The comparison is deliberately more permissive than my model scorer, and the file says why: "the goal is to surface cases where the two queries answer DIFFERENT QUESTIONS, not cases where they label the same answer differently." So it rounds floats, coerces numeric strings, ignores column names and order, flattens the $facet set-difference shape, and searches for a match under column removal to handle Mongo carrying an extra computed column.

145 of your gold queries disagree with the SQL. Doesn't that mean 10% of your ground truth is wrong?

No, and the classifier is there specifically to answer that. The 145 auto-classify into causes, and most are not gold defects:

  • 37 TIE_OR_RANK — the question is under-determined. Both answers are correct; the engines break the tie differently. Nobody's defect.
  • 50 type-related (TEXT_TYPED_NUMERIC 38 + AGGREGATE_OVER_TEXT 12) — SQLite coerces TEXT in comparisons and aggregates; Mongo does not. These are usually gold-Mongo issues and they are real, but they are one systematic cause, not 50 independent errors.
  • 15 structural (SET_OP, JOIN_FANOUT, SUBQUERY) — worth reading case by case.
  • 43 UNCLASSIFIED — genuinely unknown, and the CSV says to read these first.

Also relevant: only 36 of the 145 fall inside the 304-case test set, so the effect on published numbers is bounded. And a third benign source I'd name unprompted: Spider's own gold SQL is known to contain some wrong queries — disagreement does not automatically indict my side.

The disposition is written at the top of the file: # A disagreement is a case to READ, not automatically a broken gold query.

How did you audit your scorer, and why key verdicts by (arm, id)?

A three-stage funnel. First, drop everything AST-identical to gold ignoring formatting — those need no review, and it removes 126 cases across the three arms, which is what keeps the reviewable set human-sized. Second, flag mechanically: gold-empty, scalar gold, single narrow row, matched only via the tolerant tier, different collections touched, sort present/absent, sort specs differ. Third, a human reads the flagged cases side by side with the gold and the question.

The keying is the sharp part Verdicts are keyed by (arm, id), not by id. "A false positive is a property of a specific generated query, not of a test case." Two cases prove it: on spider-flight_2-75 and spider-apartment_rentals-29, fine-tuning's query is defective while RAG's is correct. An id-keyed registry would have blamed RAG for both.

There is also a staleness check: a verdict that no longer lands on a scored-correct case is reported as stale, because the arm was regenerated or the id moved. That is what makes a hand-curated registry safe over time.

Doesn't a hand-curated verdict registry just encode your bias?

It would if it only looked one way. Three defences.

One: both directions are audited. There is a false_negative_reason() function hunting cases scored wrong that a stricter reading says are right — 6 RAG, 2 fine-tuned, 2 baseline. If I were hunting for reasons my numbers were too high, I would not have built that.

Two: the corrections cut against the arm I favour. RAG loses 3, fine-tuning loses 9 — but RAG also gains 6 false negatives to fine-tuning's 2. Both registries record equivalences I accepted, 18 of them, including 9 reversed-$lookup cases, so reviewers don't re-litigate.

Three: one entry indicts my own gold. On spider-world_1-2 the fine-tuned query counts distinct languages where gold counts language rows — recorded as "arguably MORE correct than gold … a gold-quality question, not a model error."

And the standard is written down: "the reason is the specific semantic defect, not the flag that surfaced it — a flag is only what made someone look."

Why does the audit import the real scorer instead of reimplementing the comparison?

Because an audit that reimplemented results_match would be auditing a copy. If my reimplementation drifted from the real one — and reimplementations always drift — the audit would be measuring the error rate of a function nothing uses.

So it does from execute_queries import _canonical, _strip_null_id, _values_canonical, results_match # reuse the REAL scorer, don't reimplement it. It reproduces the tier structure to report which tier accepted a case, but the primitives are the originals.

Same principle runs through the repo: both scoring scripts import connect and run_model from one module, and four scripts import one prompt-builder. There is exactly one scoring implementation, one normaliser, one prompt header and one embedding function in this codebase — and that is what makes a three-arm comparison a controlled measurement.

Explain the characterization tests. Isn't asserting wrong behaviour just wrong?

No — an untested blind spot is invisible; a characterization test is a documented, dated, cross-referenced decision with a named cost.

Four tests assert that specific wrong queries currently score correct: empty matching empty, scalar coincidence, invisible ordering, and low-cardinality "top N". Each cites the confirmed case id it abstracts, so the test file and the audit registry cross-reference each other.

The value is what happens next: tighten the scorer and pytest tells you exactly which four assertions flip, rather than a mystery regression appearing somewhere in 100 tests. And the mirror is pinned too — test_unprojected_id_breaks_the_match is a characterization of a known false negative. Both directions.

Why did you re-score the baseline instead of reusing its existing number?

Because the existing number was computed over the full golden set — including the cases that are now the few-shot pool RAG retrieves from. Comparing RAG's test-slice score against a full-set baseline number would be comparing different test sets, not measuring what retrieval added.

So the scoring script re-executes the baseline restricted to the same held-out ids, same gold, same scoring code. It also warns if any test id is missing from the baseline file — and when the baseline input is already sliced, that filter becomes a no-op that doubles as a coverage check.

Why I'd lead with this if asked about evaluation bugs This is exactly the subtle mistake that inflates results in published work, and it is invisible in the output. Two numbers sit next to each other in a table looking comparable, and they are measuring different populations.

Four gold queries return empty. Isn't that a problem?

It is a known and bounded one: 4 of 1,517, all in flight_2, and I can name the ids. Zero of 1,517 gold queries fail to execute.

The reason it matters is the first false-positive class: empty matches empty, so on those four cases any query returning nothing scores correct. That is why the audit reports gold health first, before anything else — "a false positive caused by broken gold is a different problem from one caused by a permissive comparison", and you want to rule the first one out before diagnosing the second.

Only one of the four carries a GOLD_EMPTY flag in the current audit, so the practical exposure is small — but I'd rather state the mechanism than the reassurance.

FInterview questions — MongoDB & data

Walk me through the MongoDB aggregation pipeline as if I only know SQL.

It is an ordered array of stages, each transforming a stream of documents. The mapping is mostly one-to-one: $match is WHERE, $group is GROUP BY, $sort is ORDER BY, $limit/$skip are LIMIT/OFFSET, $project is SELECT, $lookup is LEFT JOIN, $addFields is a computed column.

Two stages have no SQL equivalent and both matter here. $unwind flattens an array field into one document per element — you almost always need it after a $lookup, because $lookup produces an array. And $facet runs several sub-pipelines in parallel over the same input, which is how you express things Mongo has no operator for.

The big difference from SQL is that order of stages is semantics, not a hint. There is no query planner reordering your predicates for you in the way a SQL optimiser does — putting $match after $lookup instead of before is a correctness-and-cost decision you make explicitly.

How does MongoDB do set operations like EXCEPT and INTERSECT?

It doesn't, directly — and that is a real gap. The gold queries express them by running two sub-pipelines inside a $facet and then comparing the resulting arrays with $setDifference-style expressions.

The consequence is a shape mismatch that my SQL cross-check has to handle explicitly: the Mongo side returns one document holding an array of the answers, where SQL returns N separate rows. So the comparison flattens that shape before comparing, and the code notes it is "common rather than exotic" — 7 of the 145 disagreements are classified SET_OP.

There is also $unionWith, which is the closest thing to UNION and reads a second collection. It is in my safe-stage allowlist — and it was added late, after re-running the guard over every stored query found 7 gold queries that used it and could no longer be regenerated.

What's the hardest thing about generating $lookup correctly?

Three things, in increasing subtlety.

One: it does not coerce types. SQL will happily join an integer column to a numeric-text column; Mongo will not. Joining str to int silently matches nothing — zero rows, no error. That is why three of my FK annotations carry an explicit str->int, use $toInt note, and why the prompt tells the model to cast.

Two: the output is an array. Forget the $unwind and every downstream stage sees a nested array instead of a field.

Three: direction is often a genuine equivalence, not a bug. Looking up A from B and B from A can produce identical result sets, which is why 9 of the 18 accepted cases in my audit registry are reversed join direction. That is a case where the naive "it doesn't match gold's structure" reading would have been wrong.

Your schema has no foreign keys. How did you get a join graph?

I mined it. MongoDB has no declared FKs, so I parsed every $lookup stage's from/localField/foreignField triple out of the gold query corpus and kept only the canonical edges — intermediate field names created by aggregation workarounds, things like "CountryInt" and "sid_int", are replaced by the real schema field name.

22 edges across 6 databases, three carrying type-mismatch warnings.

The limitation, and why it bounds a result It covers only 6 of 23 databases and the code says so openly. That directly bounds the FK A/B experiment's possible effect size — 17 databases render identically in both variants, which makes them a free implicit control and makes the observed one-case difference exactly what you would predict. An acknowledged coverage gap that explains a result is more useful than a silently partial feature.

How do you infer field types from a schemaless store?

Sample documents and take the type of the first non-null value seen for each field across all documents — not docs[0]. Field order comes from docs[0] for stable prompt output, but the resolved type scans everything and tracks a nullable flag separately.

The motivating bug is concrete: world_1.country.IndepYear is a genuine integer field, null for 47 of 239 countries, and docs[0] happens to be one of the null ones. Trusting docs[0] labelled a real integer column NoneType in the LLM-facing prompt — actively misleading, worse than omitting the field. Fields null in every document are marked "unknown, nullable" rather than guessed.

The general point: schema inference from a document store is genuinely ambiguous because there is no DDL, and the naive single-document approach produces wrong answers on exactly the columns where nullability matters.

You eval() LLM-generated code against a live database. Justify that.

It is the right threat model to be worried about, and I would not defend the eval() itself — I would defend the three layers in front of it, and then name what they still don't cover.

Layer 1 parses in mode="eval", so only a single expression is even syntactically admissible — no statements, no imports, no semicolon chaining. Then it walks the AST and rejects any underscore-prefixed attribute (that kills the __class__→__subclasses__ escape), any method not in a read-only allowlist, and any identifier outside a set of eight. That last one is the load-bearing rule: every route to arbitrary Python needs some free identifier, and there are only eight.

Layer 2 walks every dict at every depth for five forbidden operators — the JS-execution family ($where, $function, $accumulator) and the write family ($out, $merge).

Layer 3 is an allowlist of safe aggregation stages, which catches read-only-but-disclosing stages nobody would think to forbid.

Plus a 60-second socket timeout, because the allowlist bounds what a query can do and nothing bounded what it could cost.

Your first version of that guard had a hole. What was it, and how did you fix it properly?

The stage check only inspected aggregate() pipelines. So $where — arbitrary server-side JavaScript — inside a find() filter went straight through: not an aggregate() call, and to the outer AST allowlist a filter is just a literal dict. Found by writing the first test suite.

The naive fix was to read literal string keys and check them. That is also a hole, because Python evaluates dict keys at runtime. I verified four payloads that defeat it and hand a real operator to the driver: {"$o" + "ut": ...}, {f"$merge": ...}, dict([("$out", ...)]) (no ast.Dict node at all), and the same trick inside a find() filter.

The principle behind the real fix "Rather than trying to constant-fold arbitrary expressions — an endless game against str.join, .replace, %-formatting, chr() — this refuses anything it cannot statically prove is a safe literal." Non-literal key → reject. ** unpacking → reject. dict() constructor → reject. That is the move from a denylist to a sound checker: stop enumerating what is bad, start requiring proof of what is good.

Fail-closed rules usually break legitimate use. Did yours?

No, and I measured it before shipping rather than assuming: "across all 20,014 query strings in this repo's result and reference files, zero use a non-literal dict key and zero call dict(), so this rejects nothing that has ever legitimately run."

Ten of the 43 safety tests are must-keep-working regression tests for exactly this — including the dotted collection name and the two operators that were previously over-rejected.

Why that class of test is the one people skip A safety suite that only tests rejection is half a suite. False-positive rejections silently destroy your accuracy numbers, and nobody notices, because the failure looks like the model being bad. That is not hypothetical here: tightening the guard once broke reproducibility of my own gold — 7 gold queries using $unionWith and $setWindowFields could no longer be regenerated.

What's still not covered by your guard? Be specific.

The stage allowlist applies only to top-level stages of an aggregate() whose first positional argument is a literal list. So a non-forbidden, non-allowlisted read-only metadata stage nested inside a sub-pipeline gets through — I verified that $lookup → pipeline → {"$indexStats": {}} and the same inside a $facet are both allowed.

Writes and server-side JavaScript are not in that gap, at any depth, because layer 2 is depth-blind — I verified $out and $where nested in a $lookup sub-pipeline are both rejected.

So the residual exposure is metadata disclosure against a cluster the harness already has full read access to. No write, no code execution. The fix is to recurse the stage check into $lookup/$facet/$unionWith sub-pipelines, and it is a small change.

Why I'd volunteer this unprompted Knowing the exact boundary of your own guard is worth more than claiming it is airtight, and anyone who probes will find it anyway.

You have a fail-closed guard and a fail-open allowlist in the same codebase. Isn't that inconsistent?

They are different threat models, and I would argue the inconsistency is correct.

The query guard is fail-closed because its failure mode is a write or a code execution against a live cluster. If it cannot prove a query safe, rejecting it costs one scored case.

The database allowlist in the demo is fail-open — if allowed and database not in allowed — because it derives its list from schema dumps, and "a demo that refuses to run because a schema dump is missing would be a worse failure than the one this guards against." Critically, it fails open behind the fail-closed guard: whatever database you reach, the query guard still bounds what can be done there. It is scope containment, not the primary control.

Its threat model is also specific and real: a free-text input flowing into client[database] on a Streamlit app, which has no auth and binds every interface by default — on conference wifi that is reachable by anyone on the network. Placing the check at the single Atlas-touching call site means one check covers all three arms rather than three checks that can drift.

Why rewrite the model's output before executing it? Isn't that grading on a curve?

It is the most ethically dangerous step in the harness — you are editing the artifact you are grading — so let me give the four defences.

The rewrite set is minimal and enumerable: four rules. Bare null/true/ false to Python constants; countDocuments/findOne to snake_case; a zero-arg count_documents() gets an explicit {}; and an outer list() is unwrapped. Nothing semantic.

It operates at AST level, so it provably cannot touch data. Every rewrite is logged per case, because it is a silent-by-default rewrite of the model's actual output. And it is applied identically to gold and to every arm, so it cannot favour one.

The justification for existing at all Qwen was trained mostly on Mongo-shell/JS docs, not PyMongo. Those are dialect errors, not reasoning errors — the query is right and the syntax is from the wrong API. Counted: 15 null rejections and 2 countDocuments rejections across arms, zero on Claude. Scoring those as comprehension failures would have measured which documentation corpus the model saw.

Why AST rewriting rather than a regex? That's a lot of machinery for four rules.

Because a regex would corrupt real data, and I can point at the exact value.

null as a bare identifier is an ast.Name node. The literal string "null" in quotes is an ast.Constant. And "null" is a genuine field value in this dataset — cars_data.Horsepower and MPG hold the literal text "null" for some rows, which is why the prompt explicitly tells the model to write {"MPG": {"$ne": "null"}}.

So a s.replace("null", "None") regex would corrupt the very guard the prompt asks for, turning a correct query into a broken one, silently. There is a test pinning that the quoted string is left alone.

The AST version also gets a second thing right for free: ast.unparse canonicalises quote style and whitespace, which is what makes the same function usable as the equality key for self-consistency voting.

GInterview questions — engineering practice

Tell me about the hardest bug you debugged in this project.

A segfault with no traceback. rag/build_prompts.py — step 3 of my own README's reproduction recipe — died silently right after printing Embedder ready., before a single prompt was built. Exit 139. No Python-level error to catch.

The cause: the venv ships three separate copies of libomp.dylib, vendored by torch, faiss and sklearn. On macOS the dynamic loader binds the first copy loaded, process-wide. If faiss's copy wins, the first torch forward pass segfaults.

I reproduced it minimally in both directions: import faiss then torch → crash on the first model(**enc); import torch then faiss → clean run, correct results. The script imported faiss first because that is alphabetical order.

And the second-order damage is the real lesson The crash did not just fail a run. It left rag_prompts.json stale relative to the results committed beside it — a silent crash became a reproducibility corruption. That is part of what motivated building the manifest system.

How did you fix it, and did the fix hold?

At the import-order level — not KMP_DUPLICATE_LIB_OK, not symlink surgery on site-packages. A blank line separating the two imports, a # noqa: E402, and an explicit comment saying "Do not let isort merge these back into one block."

And no, the fix did not hold. It was applied in the two RAG scripts and then recurred in the demo UI's RAG tab, which imports faiss directly rather than going through build_prompts, so it never inherited the fix. There it took down the entire Streamlit process at the first embed() call — and because a SIGSEGV is not a Python exception, the app's broad except Exception could never have caught it.

The maintenance lesson, which is the real answer An invariant enforced by convention at each call site leaks the moment someone bypasses the wrapper. The correct fix is a single import-ordering shim module that every entry point imports first, so the ordering is enforced in one place rather than remembered in five. That is my honest "what would you do differently."

Your repo has manifests, a canonical-artifacts document, and 100 tests. Isn't that over-engineering for a capstone?

Every one of them was built after a specific failure, not in anticipation of one.

The manifests exist because three concrete problems had already happened: the segfault meant a committed prompts file did not match the results beside it (103 of 304 cases differ on regeneration); the baseline arm was generated when two databases had no local dump, so 181 of 304 cases regenerate differently; and neither was detectable from anything in the repo.

The canonical-artifacts document exists because results are spread across five directories and several superseded files sit unmarked beside current ones under near-identical names — three qwen_rag_mlx_*results.json variants, four generations of finetuned_full304*. Nothing in a filename says which is authoritative, so a reader picks by guess.

The tests exist because the scoring code had been extended four times, each time by reasoning rather than pinning behaviour, and each extension made the comparison more permissive — and writing the first suite immediately found a $where injection hole.

The one-sentence version: "a metric change cannot be attributed to a cause if the artifact does not record what the cause was."

Why a sibling manifest file rather than a key inside the results JSON?

Because every results file in this repo is a JSON list, and every consumer does json.load(f) and immediately iterates it — the normaliser, both scorers, the executor, the visualisers, the demo. Turning the top level into a dict to hold a _manifest key would break all of them at once.

So: <stem>.manifest.json. Purely additive, impossible for an existing reader to trip over, and it survives the results file being regenerated by a resumable run.

The general principle When you add metadata to an existing artifact format, ask what the readers assume about its shape. The cheapest safe place for new metadata is usually beside the thing, not inside it.

Your manifests record git_dirty: true on every run. Isn't that a red flag?

It is honest, and it is deliberately recorded rather than enforced. The comment says why: "a dirty-tree run is a legitimate thing to do while iterating, it just must not be mistaken later for a run that pins to a published commit."

The flag is also tri-state — True, False, or None when git is unavailable — because collapsing "unknown" into "clean" would be worse than useless.

The alternative, refusing to run on a dirty tree, would have made every exploratory run impossible and would have been disabled within a day. A provenance system people turn off records nothing.

Same philosophy runs through the git capture: it is best-effort with a 10-second timeout, because "a manifest that is missing its SHA is far better than a generation run that dies at the finish line because git is not installed."

Give me an example of choosing not to fix something.

Two, and they are instructive together.

The one I fixed: college_1/2/3 landing in one training batch. A prompt-construction bug with a clean, low-risk fix — add a collision-groups list and a greedy first-fit placement. college_3 went from 0/7 to positive double digits.

The one I didn't: chinook_1 and store_1 being the same data under two naming conventions, which makes 9 test cases structurally unretrievable. Merging them would need every one of ~42 gold queries rewritten into the other's naming and verified not to touch the two collections where the data genuinely differs — InvoiceDate (offset by two years) and PlaylistTrack (different membership) — where a careless merge produces a wrong-but-plausible answer. That is a high-risk change to my ground truth for a 9-case gain.

So I verified the claim (9 of 11 collections byte-identical), documented the two exceptions, wrote down why it is unfixable by retrieval at all, and left it. Knowing which bugs to leave alone, and writing down why, is a skill.

What does "reuse, don't reimplement" mean concretely in this repo?

It is enforced by import, not by convention, and there is a recurring comment marking it: # noqa: E402  reuse, don't reimplement.

Concretely: both scoring scripts import connect and run_model from one module, so there is exactly one scoring implementation. Four scripts — including the demo — import build_full_schema_system_prompt from the baseline generator, so the prompts are byte-identical. The index builder and the query-time retriever import the same embed(). The false-positive audit imports the real results_match rather than reimplementing it. And generation_utils.py exists precisely because five scripts across all three arms were importing production post-processing from a script whose own docstring said "not a scored metric, just does this look sane" — which misrepresented what it is.

Why this is the point, not a style preference It is what makes a three-arm comparison a controlled measurement. If each arm had its own prompt builder, its own post-processing and its own scorer, any difference between arms would have four candidate causes.

How do you make a long generation run survivable?

Checkpoint after every single case, not every N. A 304-case k=5 self-consistency run is 1,520 generations; losing it at case 300 is unacceptable, and the write is cheap relative to a generation.

Three details that matter more than the checkpointing itself. Results are held in a dict keyed by id but written in original prompt-file order, so a resumed run produces the same file layout as a straight-through run — which matters for git diff sanity and for any consumer that zips by position. A corrupt checkpoint degrades to "start fresh" with a warning rather than crashing, because a truncated JSON from a kill mid-write should not be unrecoverable. And resume is id-based skip, so the same mechanism also lets you top up a run after adding cases.

Self-consistency also writes to its own output file, so a crash mid-sampling cannot damage the greedy results.

Show me a validation guard you're proud of.

--samples > 1 with --temp 0 is a hard error, not a warning:

"--samples > 1 with --temp 0 would generate k identical greedy completions and
 report a self-consistency of 1.0 for every case -- a meaningless number that
 looks like a result."

The asymmetry is the design. This is an error because the bad output is plausible: self_consistency = 1.0 across all 304 cases looks like a spectacular finding rather than a bug, and would sail into a slide deck. Meanwhile --samples 1 --temp 0.7 is only a warning, because a single stochastic generation is unusual but legitimate.

Fail loudly on the silently-wrong case; warn on the merely surprising one. The same principle shows up in the schema-card fallback, which raises rather than returning an empty schema, because an empty schema produces a completed pipeline with plausible numbers for a different experiment than you think you ran.

Your requirements.txt has a dependency conflict you didn't resolve. Explain.

codebleu==0.7.0's declared PyPI metadata requires tree-sitter<0.23, but tree-sitter-python==0.23.6 requires ≥0.23. The intersection is empty on paper. Because pip resolves the whole file jointly, it refuses to proceed.

But it is a declared-metadata conflict, not a runtime incompatibility — tree-sitter 0.23.2 and codebleu 0.7.0 are installed together in this venv and have been computing CodeBLEU scores successfully. codebleu's setup metadata is simply stricter than what actually works.

The workaround is documented in the file: install mlx-lm standalone rather than via -r, which resolves only its own unrelated tree, leaving the already-working pair untouched. And there is an explicit "don't try to fix this by loosening the pin" note, because any range satisfying both declared bounds would be empty.

Why the pin is hard A bare codebleu let pip backtrack to 0.6.1, which bundles tree_sitter_languages and compiles multi-language grammar C at install time — and that compile fails on Apple Silicon with ld: symbol(s) not found for architecture arm64. Pinned so the resolver never considers it again.

HInterview questions — system design

Productionise this. What does the architecture look like?

Five components, and the shape follows directly from what I measured.

1. Schema service. Introspect the live database on a schedule, emit schema cards with inferred types and mined join edges. This is the thing that goes stale and silently degrades everything downstream, so it gets versioning and a freshness check, not a cron job and hope.

2. Retrieval index over a growing corpus of verified question→query pairs. At 1,213 vectors exact search is right; past ~105 I'd move to HNSW and accept approximate recall.

3. Generation with the RAG prompt. I would not lead with fine-tuning, for a reason that is not about accuracy: retrieval generalises to a new database by adding a row; LoRA generalises by retraining. In production, schemas change weekly.

4. A confidence gate, which is the part my numbers most support — see the next question.

5. The execution sandbox, unchanged in structure, but with a read-only database user, which is the control I lean on hardest and did not have.

Users won't accept 47% accuracy. How do you ship this?

You don't ship it as an autonomous answer engine. You ship it with a confidence gate, and I have the numbers to size one.

Self-consistency at k=5 gives 81.5% accuracy on the 54 cases where all five samples agree, 60.7% in the middle band, and 22.4% below 0.6 agreement. That is a 3.6× spread — a usable coverage/accuracy curve.

So: auto-execute above the high threshold (~18% of traffic at 81.5%), show the query for human review in the middle band, and escalate to a larger model or refuse below. The cost is 5× inference on gated traffic, which is the honest price and is measurable.

Two things that make it more shippable than the raw number suggests First, users see and can edit the generated query — a wrong query that is visibly wrong is a very different product failure from a wrong number presented as fact. Second, every accepted query becomes a new retrieval exemplar, so the system improves with use without retraining. That flywheel is another argument for the retrieval architecture.

How would you route between RAG and fine-tuning, given they're complementary?

The headroom is real: union is 180/304 = 59.2% against RAG's 142 alone, so a perfect router would gain 12.5 points.

The cheapest version is not a router at all — it is ensembling. Run both arms, and when they agree, confidence is high (they agree on 64 cases, and agreement across two differently grounded systems is a stronger signal than agreement across five samples of one). When they disagree, you have 116 cases to arbitrate, and you can afford an expensive arbiter on 38% of traffic.

A learned router would need features: self-consistency per arm, mean logprob, retrieval score distribution (is the top neighbour close, is the neighbourhood flat), predicted-database vote margin, and question complexity. I have all of those persisted — that is partly why the FAISS scores and the full per-token logprob vectors are on disk.

What I'd check first Whether the 59.2% union is even reachable, by testing whether my confidence signals separate the RAG-only cases from the FT-only cases. If both arms are equally confident when wrong, the oracle gap is not addressable and the honest answer is to ensemble rather than route.

How do you keep this from breaking when the schema changes?

This is the failure mode I have direct evidence for, so I'd design against it specifically.

What happened in my repo: the baseline prompt is assembled at runtime from whatever is dumped locally. When two databases had no dump, the prompt silently omitted their schema, and 181 of 304 cases regenerated differently. Nothing errored. And on a clean clone the whole schema went missing and the arm built a schema-free prompt and completed successfully.

So, three controls. Version and hash the schema, and record that hash in every artifact — which is what my manifests now do, including a schema_coverage block listing covered and missing databases. Fail loudly on missing schema, never return empty: my card builder raises rather than returning [], with a three-tier live→snapshot→raise fallback where the snapshot logs a loud warning that it is a snapshot. And make a schema change trigger re-evaluation, because a stale retrieval corpus referencing renamed fields will confidently produce queries against columns that no longer exist.

For fine-tuning specifically, a schema change means retraining, which is the strongest architectural argument against putting it on the critical path.

What are the security requirements for a system like this in production?

Layered, and I'd start with the one I did not have.

A read-only database user. My guard blocks $out, $merge and the write methods at the AST level, and I tested that thoroughly — but defence in depth means the credential itself should be incapable of writing. That makes every guard bug a disclosure bug instead of a destruction bug.

Then: the AST allowlist and forbidden-operator walk as I have them; per-query maxTimeMS rather than my connection-level socket timeout (I use the coarse version because eval()ing an arbitrary expression gives no single call site to attach a limit to — in production you'd generate through a builder that does); row limits on returned results; per-user rate limiting; and query logging with the generating prompt attached, because you will need to explain a bad answer after the fact.

And the boring one: auth in front of the UI. My demo needed a database allowlist specifically because Streamlit has no auth and binds every interface by default.

Where would you spend the next month?

In order of expected value per unit of effort:

  1. Selective prediction. The confidence data already exists — all 1,520 samples and full logprob vectors are persisted. Compute ECE and a reliability diagram, fit a threshold, report a coverage/accuracy curve. That converts 46.7% into a shippable product characteristic.
  2. Mask the prompt in training. One config key. Most of my LoRA gradient signal is currently the model re-predicting its own fixed system prompt.
  3. Re-run the K sweep on the current stack. My K=10 choice rests on a sweep run on the noisy Colab stack at n=61, which is exactly the evidence I later argued was unreliable. Also test exemplar ordering, which I never ablated.
  4. Read the 72 unreviewed audit candidates. Cheap, and it is the number I am least confident in.
  5. A retrieval reranker, since I now know retrieval is at 84.9% while end-to-end is 46.7% — though the diagnostic says generation is the bottleneck, so this is fourth for a reason.

What I would not do first: train a bigger adapter. The 8.48% out-of-scope generalisation result says the returns there are narrow.

If you had 10× the data, would fine-tuning win?

Probably it would close a lot of the gap, and I can say why with more than intuition — I have a scaling data point of my own. Going from 219 training examples on 6 databases to 1,091 on 23, at matched epoch coverage, is the difference between the arm being unusable and 33.9%.

But there are two reasons I would not expect it to overtake, and one reason it might not matter.

One: my false-positive analysis says fine-tuning's errors are a specific kind — structurally plausible pipelines with wrong predicates. More data teaches shape faster than it teaches precision, so I would expect the FP rate to persist even as accuracy rises, and the corrected gap to close more slowly than the raw one.

Two: 10× the data still does not fix generalisation to unseen schemas, which was 8.48%.

And the reason it might not matter: the 10× data would have to be hand-verified gold. At my rate that is the dominant cost of the entire project. RAG gets better from the same data without a training run, so on a cost-per-accuracy-point basis retrieval is ahead even in the scenario where fine-tuning eventually wins on accuracy.

How would you evaluate this in production where there's no gold?

Four sources, roughly in order of signal quality.

Execution telemetry, which is free: what fraction of generated queries error, and what fraction return zero rows. My baseline arm's 172-empty result shows how diagnostic the empty rate alone is — a rising empty rate is an early warning that schema has drifted.

Implicit user feedback: did the user run the query, edit it before running, or abandon it? An edit is a labelled correction and the edited query is a new gold candidate.

Self-consistency as an online proxy, since it needs no ground truth — sample k times and track the agreement distribution. If mean agreement drops, something changed. I measured 0.564 mean agreement offline, so I have a baseline to alert against.

A held-out golden set that never enters the retrieval corpus, re-run on every deploy. That is the only source that gives you a real accuracy number, and it is worth the cost of maintaining a few hundred cases — which is essentially what this whole project is.

What's the latency and cost profile of your RAG arm?

Per query: one MiniLM forward pass on CPU (small, single-digit milliseconds), one FAISS scan over 1,213×384 floats (sub-millisecond), then generation over a ~5,755-character prompt with max_tokens=300.

And a real inefficiency I'd flag Because of an mlx-lm bug, every generation runs the full 300 tokens regardless — the model correctly emits <|im_end|> after the answer, but the tokenizer wrapper only checks a single eos_token_id and Qwen declares several, so it never stops. Across 304 RAG cases only 19,876 of 22,139 tokens survive post-processing. That is roughly a 3–5× slowdown I accepted because correctness mattered more than throughput for a benchmark — in production it is the first thing to fix, at the serving layer.

What I did not measure and would want before quoting a cost: tokens per query, TTFT versus inter-token latency, and rupees per thousand queries. Prompt length drives prefill specifically, which is compute-bound and scales with prompt tokens — so RAG's long prompts are a real serving cost my accuracy table does not show.

IInterview questions — adversarial & narrative

You reversed your own published conclusion. Why should I trust the new one?

Because the reversal came with a mechanism and a control, not just a different number.

The mechanism: two arms were on Colab fp16, one on MLX bf16. You cannot attribute a delta between arms to the technique when the arms did not share a runtime.

The control: I verified fp16 GPU inference is not bit-identical across separate Colab sessions, even under greedy decoding — by making a prompt change and its full revert back-to-back within one session and getting byte-for-byte identical output. Since the code returned to its exact prior state and the output matched, an earlier apparent accuracy swing attributed to that change could only have come from a session boundary.

And the new stack has the property the old one lacked: two independent full 304-case runs came out identical down to the per-token logprobs.

The thing to notice I did not caveat the confound — I removed it, rewrote two arms onto one stack, published the reversal, kept the old scripts labelled as historical, and built a figure showing both runs side by side. Trust the second conclusion more because the first one's failure was diagnosed, not because it is newer.

Your best arm gets under half the questions right. Isn't this a failed project?

Only if the goal was a product. It was a controlled comparison, and it produced clean answers to the question it asked.

Look at the deltas rather than the level: 4.9% → 46.7% is a 9.5× improvement from retrieval alone, on a model small enough to run on a laptop, with no weight changes. The comparison between adaptation strategies is decisive at ~4 standard errors. And the mechanism behind the winner is explained, not just observed — fine-tuning's false-positive rate is 4× higher, in exactly the way "learning shape rather than semantics" predicts.

I would also point at the ceiling: 37 test questions are provably under-determined, 9 are structurally unretrievable, and 4 gold queries return empty. 46.7% against a ceiling meaningfully below 100% reads differently from 46.7% against a clean 100%.

And the honest version: for a production text-to-query product, none of these arms is shippable autonomously. What is shippable is the gated version — 81.5% on the 18% of traffic where five samples agree.

Isn't this just prompt engineering with extra steps?

The retrieval arm is prompt construction — but the contribution is not the prompt, it is that the comparison is controlled and the measurement is execution-based.

The prompt header, rules and output contract are identical between baseline and RAG, on purpose — "the only real difference between baseline and RAG prompts is retrieved content … not prompt template drift." If the template also differed, the +41.8-point delta could be attributed to better instructions rather than to retrieval. That control is what makes it a measurement rather than an anecdote.

And the parts that are not prompt engineering: an execution-based scorer with an audited error rate, a ground-truth cross-check against an independent query language, a fine-tuning arm with two diagnosed methodology bugs, provenance manifests, and two confidence signals with a measured coverage/accuracy curve.

You used a lot of hand-written rules and hand-curated verdicts. Doesn't that make this unscalable?

Some of it, yes, and I'd separate the two cases because they scale differently.

The prompt rules are seven lines of distilled error classes and they scale fine — they are generic MongoDB and scoring facts, not per-database. The FK edges and the type warnings are per-database and genuinely do not scale: FK covers 6 of 23 databases and the type note covers 6, and both are stated as open work rather than quietly partial.

The verdict registry is hand-curated by design, but with two scaling mitigations: an AST-identical filter removes 126 cases before any human looks, and mechanical flagging narrows 912 arm×case combinations to 114. So the human reads ~100 cases, not 900.

What would actually scale The FK mining is already automated — it parses gold $lookup stages — it just was not re-run after the corpus tripled. The type warnings are derivable from the schema cards, which already record inferred types, so they could be generated rather than hand-listed. Neither is a hard problem; both are honest debt.

What would you do differently if you started over?

Five things, in order of how much they cost me.

Unify the serving stack from day one. The confound cost a whole round of conclusions and every figure had to be regenerated.

Write the scorer's tests before extending it four times. Each extension made the comparison more permissive; the tests came last and immediately found a $where injection hole.

Build the manifests before the first generation run, not after three artifacts had already gone stale.

Compute epoch coverage, not iteration count, whenever the corpus changes. That one number cost 9.9 points and a wrong conclusion.

Enforce the import-order invariant in one shim module, not by convention at every call site — because it leaked to a fourth site and took down the demo.

The pattern across all five: every one is a case where I relied on a property being true rather than making it structurally impossible to violate.

What surprised you most?

That CodeBLEU could not tell my two arms apart at all. 0.2783 versus 0.2759 — 0.0024 — on two systems separated by 12.8 points of actual correctness. I expected the metrics to correlate weakly. I did not expect them to be effectively blind.

Digging into the components made it worse and more interesting: n-gram match is ~0.01 for every arm, so almost the entire score is AST syntax match. CodeBLEU here is measuring "did you produce a well-shaped PyMongo expression" — which every arm mostly does.

The second surprise was directional: fine-tuning scores higher on n-gram match than RAG while scoring 12.8 points lower on execution. It learned to imitate the reference's token sequence more closely and compute the right answer less often. That is the entire mechanism of the result, sitting visible in a metric I had almost dismissed as a formality.

Convince me you understand this deeply rather than having followed a tutorial.

Three things a tutorial would not have produced.

I read my adapter's weights back to check what I trained. 224 tensors, layers 12–27, seven modules, summing to 10,551,296 parameters — matching the trainer's log line. And the shapes told me something the config did not: k_proj/v_proj output 256 while q_proj outputs 1536, which is the GQA signature — 12 query heads, 2 KV heads, head_dim 128. You can read the attention architecture off the adapter file.

I found a bug in a metric library. CodeBLEU's composite computes theta * (dataflow_match_score or 1), and 0.0 or 1 is 1 in Python — so a degenerate component silently becomes a perfect one. I verified it arithmetically against my own CSV before excluding the component.

I diagnosed a serving-library bug and refused to work around it in the wrong place. mlx-lm's wrapper checks a single eos_token_id; Qwen declares several. The model is correct, the library is wrong. I fixed it at the string layer rather than patching site-packages — and then noticed it corrupts the confidence signal, not just throughput, because averaging logprobs over a discarded tail describes text that was thrown away.

Sell me the one thing from this project you'd want a team to adopt.

Audit your scorer, in both directions, with verdicts keyed to the artifact rather than the test case.

Everyone measures models. Almost nobody measures the measurement. My scorer admits four specific classes of wrong-but-passing query — and until I audited it, I did not know whether that was a 1% problem or a 20% problem. It turned out to be 2.1% for one arm and 8.7% for another, which is not noise: it is a systematic difference that changes the size of the headline result.

Three details make it work. Both directions — hunt false negatives too, or you are hunting for reasons your numbers are too high. Keyed by (arm, id) — a false positive is a property of a generated query, not of a test case, and I have two cases proving an id-keyed registry would have blamed the wrong arm. And a flag is a reason to read, never a verdict — mechanical heuristics narrow the set, humans decide, and verdicts go stale loudly when the artifact changes.

Then pin the known blind spots as characterization tests, so tightening the scorer later is a visible assertion flip rather than a mystery regression.

Scope and generality

  • Dense retrieval only. No BM25 baseline, no hybrid, no reranker. Those are the obvious ablations I do not have.
